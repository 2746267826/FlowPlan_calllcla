三、当前重新确认的核心目标

FlowPlan 接下来的重心，不再只是继续堆叠追踪展示，而是回到“任务、日程、提醒、排期、追踪联动”这一主线，并以 Outlook 作为可选的跨设备同步底座。

新的总目标是：
- 不自建服务器的前提下，利用 Outlook 完成任务和日程的跨设备同步
- 绝对不能破坏用户原有的 Outlook 正常日程数据
- 所有任务和日程都必须严格从属于任务本或日历本，不能孤立存在
- 提醒机制必须从“有设置项”进化到“真正可靠可触达”
- 智能排期必须与追踪闭环联动，而不是静态排完就不管
- 工作时间模型必须支持多组时段，而不是只支持单段工作时间
- 安卓端要逐步适配为任务 / 日程 / 追踪查看与同步终端

五、P0：Outlook 同步模型重构与安全边界建立

1. 目标

把当前“只读 / 完全不同步”的粗糙模型，升级为真正可用的三态同步模型：
- 只读
- 双向同步
- 暂停同步

2. 同步模式语义

2.1 只读
- 保留账号连接状态
- 保留本地与 Outlook 的映射关系
- 允许从 Outlook 拉取日历与事件更新
- 不允许 FlowPlan 向 Outlook 写入任何变更

2.2 双向同步
- 保留账号连接状态
- 允许从 Outlook 拉取更新
- 允许 FlowPlan 把本地可同步内容回写到 Outlook
- 但回写范围必须受控，不能默认写入所有 Outlook 容器

2.3 暂停同步
- 保留账号连接、令牌、容器映射和历史同步状态
- 暂时停止所有主动拉取与推送
- 不应等价于“断开账号”
- 用户恢复同步后应能继续沿用原先映射关系

3. Outlook 安全原则

后续所有 Outlook 双向同步都必须遵守以下安全边界：
- 绝不覆盖没有明确 FlowPlan 所有权标记的远端对象
- 绝不对普通用户日历中的未知事件执行批量写入、删除或重命名
- 绝不把任务直接混进用户原本的普通日历里
- 默认只对 FlowPlan 管理的专属容器执行回写
- 所有删除都优先走“软删除 / 归档 / 映射解除”策略，而不是直接远端物理删除
- 初版遇到冲突时，宁可进入确认态，也不能静默覆盖用户数据

4. 任务利用 Outlook 做同步的核心方案

4.1 总体思路
- 任务不直接依赖 Outlook Tasks 模型
- 任务以“独立 Outlook 日历本中的规范化镜像事件”形式存储
- 每个任务本可以映射到一个专属 Outlook 日历本
- 这些专属容器专门给 FlowPlan 使用，不干扰用户正常日程

4.2 为什么这样设计
- 用户不需要自建服务器
- Outlook 自带跨设备同步能力
- 任务可以在 Outlook 侧保留可读性
- FlowPlan 依然可以保留自己的任务语义与智能调度能力
- 与普通日历隔离后，误写入和误覆盖风险显著降低

4.3 必须满足的约束
- 专属 Outlook 日历本命名应清晰，能让用户识别这是 FlowPlan 管理容器
- 普通 Outlook 日历默认只读，除非用户明确授权绑定为可回写容器
- 任务镜像必须具备稳定的本地 ID / 远端 ID / 所有权元信息
- 镜像正文必须“人可读”，不能完全是一堆不可读元数据
- 同时仍要保留结构化元信息供同步引擎识别

5. Outlook 数据模型规划

5.1 全局同步状态
- Outlook 连接状态
- 当前同步模式：只读 / 双向同步 / 暂停同步
- 最近同步时间
- 最近同步结果与错误信息

5.2 容器映射
- 本地日历本 <-> Outlook 日历容器 映射
- 本地任务本 <-> Outlook 专属任务镜像日历容器 映射
- 容器是否允许双向写入
- 容器是否属于 FlowPlan 托管

5.3 项目级映射
- 本地事件 ID <-> 远端事件 ID
- 本地任务 ID <-> 远端镜像事件 ID
- 最近同步版本 / delta token / etag / 修改时间

6. Outlook 冲突策略规划

初期建议采用保守策略：
- FlowPlan 托管容器内的数据，优先保证“映射可追踪”
- 若本地与远端都发生修改，先标记为冲突候选
- 对关键字段冲突采用“提示用户选择”或“保留本地并记录远端差异”的保守方案
- 在稳定之前，不做复杂自动合并

7. Outlook 设置页目标

设置页中应清晰拆分以下概念：
- 账号是否已连接
- 当前同步模式
- 哪些日历本参与同步
- 哪些任务本映射到 Outlook 专属容器
- 哪些容器允许双向同步
- 最近一次同步时间与结果
- 手动同步入口
- 暂停同步入口
- 断开账号入口

六、P1：日历本 / 任务本规则补全

1. 核心原则

所有日程必须属于某个日历本，所有任务必须属于某个任务本。
日历与任务不能以“无容器”的形式独立存在。

2. 当前要补齐的规则

2.1 容器级默认策略
- 日历本可设置默认是否“阻挡自动排程”
- 任务本可设置默认是否允许自动排期
- 日历本 / 任务本可设置默认提醒策略
- 新建任务 / 日程时自动继承容器默认值，条目级可覆盖

2.2 归档与删除规则
- 删除日历本前必须处理其下属日程
- 删除任务本前必须处理其下属任务
- 对于同步容器，删除动作必须区分：
  - 本地删除
  - 解除同步绑定
  - 远端容器归档
- 归档后的容器不应继续参与自动排期和默认新建入口

2.3 导入导出
- 本地数据库中的日历本 / 任务本 / 任务 / 日程关系必须完整可导出
- 导入时需要保留容器归属关系
- 若未来导出到 Outlook 专属容器，也要保留清晰映射边界

3. “阻挡自动排程”需求落实方向

用户已明确提出：
- 不只是单个任务可设置“阻挡自动排程”
- 日历本层面也应有默认开关
- 例如“课表”这类日历本应默认阻挡自动排程

因此后续规则应为：
- 日历本默认值
- 条目继承
- 条目级可覆盖
- 排期器在计算时优先看条目级，未覆盖时回退容器默认值

七、P2：提醒系统落地

1. 总体目标

提醒不能只停留在设置项和字段层面，必须真正变成可触达、可恢复、可跨平台工作的系统提醒能力。

2. 日程提醒

日程提醒应当以“确定性提醒”为核心：
- 用户设置了提醒
- 到达提前提醒时间
- 系统必须发出通知

平台目标：
- Windows：右下角系统强提醒为主，应用前台可叠加应用内提示
- Android：使用本地通知与精准闹钟能力，避免依赖后台常驻保活

3. 任务提醒

任务提醒不能只有截止时间提醒，应升级为智能提醒体系：

3.1 截止风险提醒
- 根据 ddl、剩余预计时长、优先级、近期完成进度动态判断

3.2 计划开始提醒
- 当任务被排进具体时段后，在开始前按规则提醒

3.3 偏离计划提醒
- 如果当前应该做某任务，但追踪显示持续在做无关活动，则触发应用内提示

4. 提醒恢复能力

提醒系统应支持：
- 应用重启后恢复
- 设备重启后恢复
- 时区变化后重新计算
- 同步数据更新后重排提醒

5. 设置项目标

设置中后续应支持：
- 默认日程提前提醒时间
- 默认任务提醒策略
- 是否启用智能任务提醒
- Windows 提醒开关
- Android 精准提醒能力状态展示

八、P3：智能排期核心升级

1. 当前问题

现有排期逻辑仍偏静态，且工作时间模型过于简单，不足以支撑真实使用。

2. 多组工作时间

必须从“单一开始时间 + 单一结束时间”升级为“多组工作时段”：
- 支持例如上午、下午、晚间三段工作时段
- 支持中午休息、晚饭休息等不工作区间
- 支持不同星期使用不同规则

3. 排期输入要素

排期器后续应综合以下信息：
- 固定日程占用
- 日历本阻挡自动排程设置
- 任务本默认调度策略
- 任务优先级
- 任务预计时长
- 是否允许拆分
- 截止时间
- 是否锁定
- 当前工作时间窗口

4. 重新排期能力

当计划被打断时，系统应能：
- 识别受影响任务
- 判断是否可顺延
- 只重排允许自动排期的内容
- 不改动固定日程
- 不改动锁定任务

九、P4：追踪与排期双向联动

1. 目标

追踪不只是统计展示，而要成为排期执行反馈源。

2. 联动规则

2.1 正常执行
- 若某任务已安排在当前时段
- 追踪显示用户正在做与该任务一致的活动
- 则系统不干预

2.2 偏离执行
- 若某任务已安排在当前时段
- 追踪显示用户持续在进行明显不相关活动
- 例如游戏、娱乐、社交等
- 系统弹出提示：是否将当前任务及后续可自动排期任务向后顺延

2.3 用户确认后动作
- 重新计算后续自动排程
- 更新相关提醒时间
- 保留改动日志，避免用户失去可解释性

3. 追踪融合前提

为了让这条链路成立，需要先完成：
- 追踪数据与任务 / 日程的语义映射
- 应用分类质量提升
- “当前计划项”和“当前追踪项”的可比较模型

十、P5：安卓端任务 / 日程 / 追踪体验补齐

1. 安卓端总目标

安卓端当前不做键鼠记录，但任务、日程、追踪查看与同步完全有价值。
安卓应当被定位为：
- 日程查看与操作终端
- 任务查看与同步终端
- 追踪导入与展示终端
- 提醒触达终端

2. 追踪展示要求

用户已明确提出：
- 安卓端追踪应显示应用名，而不是包名

因此后续要统一：
- 存储技术标识与展示名分离
- UI 一律优先展示应用名
- 包名只在高级信息或调试态显示

3. 安卓提醒要求

安卓端后续提醒机制应遵循：
- 事件提醒可依赖本地调度
- 任务提醒可依赖本地重算与精准闹钟
- 不强依赖后台常驻

4. 安卓平台差异化设置

安卓端不应展示：
- 托盘相关设置
- Windows 开机自启动相关设置

安卓端应展示：
- 通知权限状态
- 精准提醒能力状态
- Outlook 连接与同步状态

8. 当前是否可以 Release

结论：当前不建议作为正式公开 Release 发布；可以考虑作为内部测试版 / 自用预览版使用。

不建议正式 Release 的原因：
- 尚未完成用户环境下的 Windows 与 Android 构建验证记录
- 提醒系统与智能排期核心已完成主线闭环，但尚未完成用户环境下的跨平台长时间稳定性验证
- Outlook 双向同步的 P6 主线能力已完成，但仍需要用户在真实账号与真实容器上继续验证长期稳定性与边界行为
- Android 端已完成 P5 基础适配，仍建议在真机手机 / 平板上继续做视觉细节与长时间稳定性验证
- 追踪与排期已经形成偏离检测、确认顺延、自动重排的 P4 闭环，但仍需要真实使用场景下继续校准偏离识别规则
- 可拆分任务已具备排程片段持久化与时间轴渲染，但仍需要经过用户本地构建和真实数据验证
- 键鼠记录、追踪日志、Outlook 同步都涉及敏感数据，正式发布前需要补齐隐私说明、权限说明与数据位置说明
- 当前最近一轮改动没有在本对话中运行构建或静态分析校验；按照项目约定，相关校验应由用户在本地手动执行并反馈结果

如果只作为内部测试版 / 自用预览版，需要至少补齐以下信息：
- [ ] Windows 构建结果：构建时间、构建命令、是否成功、生成物位置

- [ ] Android 手动冒烟测试结果：启动、Usage Access 授权、手动刷新追踪、任务 / 日程查看、移动端布局
- [ ] Outlook 安全测试结果：只读模式不写入、暂停模式不拉取不推送、双向模式只写 FlowPlan 托管容器
- [ ] 数据安全测试结果：数据库导出、待恢复副本、恢复前备份、`.ics` 智能合并、仅追加、清空后导入
