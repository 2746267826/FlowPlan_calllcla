# 第一部分：D 离线同步与冲突处理

## 1. 目标

离线同步是 FlowPlan 的基础可信层。目标不是简单“能上传下载”，而是保证：

1. 客户端断网时仍然可以正常创建、修改、删除核心数据。
2. 本地修改会进入离线队列，不丢失。
3. 网络恢复后可以可靠推送到服务端。
4. 其他设备可以拉取服务端变更。
5. 多端同时修改同一对象时，不静默覆盖。
6. 冲突进入候选，由用户人工确认。
7. 每个关键同步动作都可追溯。

一句话目标：

```text
本地可用，服务端可信，多端一致，冲突可见，操作可追溯。
```

---

## 2. 用户流程

### 2.1 普通在线流程

```text
用户在 Windows 客户端创建任务
  -> 本地数据库立即写入
  -> UI 立即显示任务
  -> 创建一条 offline_mutation
  -> 同步引擎检测网络可用
  -> 推送到服务端 /sync/push
  -> 服务端写入事实库和 change_log
  -> 客户端收到成功结果
  -> 本地 sync_object_states 标记为 synced
  -> UI 显示“已同步”
```

用户感受：创建任务应该立刻成功，不应该等服务端响应才显示。

### 2.2 断网写入流程

```text
用户断网时修改日程
  -> 本地数据库立即修改
  -> 写入 offline_mutation
  -> sync_object_states 标记为 pending
  -> UI 显示“等待同步”
  -> 网络恢复后自动或手动同步
  -> 成功后改为 synced
```

用户感受：断网时也能用，但能明确看到“还没同步”。

### 2.3 同步失败流程

```text
用户修改任务
  -> 本地成功
  -> 推送服务端失败
  -> offline_mutation 保留
  -> sync_object_states 标记为 failed
  -> UI 显示“同步失败，可重试”
  -> 用户点击重试或下次自动重试
```

失败不能导致本地数据回滚，除非用户明确撤销。

### 2.4 多端冲突流程

```text
Windows 修改任务标题：写报告
Android 离线时修改同一任务标题：写课程报告
两端先后同步到服务端
服务端发现同一字段基于不同版本修改
  -> 不直接覆盖
  -> 生成 sync_conflict
  -> 两端 UI 显示冲突
用户打开冲突处理页
  -> 看到本地版本、服务端版本、字段差异、修改时间、设备
  -> 选择保留某一方或手动合并
  -> 确认后写入最终版本
  -> 记录审计
```

用户感受：系统不能悄悄帮我覆盖，必须让我知道哪里冲突。

## 4. 服务端实现

建议 NestJS 模块：

```text
server/src/modules/sync/
  sync.module.ts
  sync.controller.ts
  sync.service.ts
  sync.repository.ts
  conflict.service.ts
  change-log.service.ts
  sync.types.ts
```

### 4.1 `/sync/push`

职责：接收客户端 pending mutations。

输入：

```json
{
  "deviceId": "...",
  "mutations": [
    {
      "idempotencyKey": "...",
      "objectType": "task",
      "objectId": "...",
      "operation": "update",
      "baseVersion": 3,
      "payload": { "title": "写报告" }
    }
  ]
}
```

处理规则：

1. 校验设备身份。
2. 按 mutation 顺序处理。
3. 使用 idempotency_key 防止重复提交。
4. create：如果服务端不存在，创建对象并生成 version 1。
5. update：检查 baseVersion 是否等于服务端当前 version。
6. 如果一致，应用更新，version + 1，写 change_log。
7. 如果不一致，进入冲突检测。
8. delete：软删除，不物理删除。
9. 返回每条 mutation 的结果。

返回：

```json
{
  "results": [
    {
      "mutationId": "...",
      "status": "applied",
      "serverId": "...",
      "serverVersion": 4
    },
    {
      "mutationId": "...",
      "status": "conflict",
      "conflictId": "..."
    }
  ]
}
```

### 4.2 `/sync/pull`

职责：让客户端根据 cursor 拉取变更。

输入：

```json
{
  "deviceId": "...",
  "sinceChangeId": 12345,
  "limit": 500
}
```

输出：

```json
{
  "changes": [
    {
      "changeId": 12346,
      "objectType": "task",
      "objectId": "...",
      "operation": "update",
      "version": 4,
      "payload": {}
    }
  ],
  "nextCursor": 12800,
  "hasMore": false
}
```

规则：

- 不要一次拉全量。
- 支持分页。
- 支持软删除事件。
- 客户端 ack 前不要轻易移动本地 cursor。

### 4.3 `/sync/ack`

职责：客户端确认某批 change 已落地。

规则：

- 客户端只有在本地数据库写入成功后才能 ack。
- ack 后服务端更新 device_sync_cursors。

### 4.4 `/sync/conflicts`

职责：查询和解决冲突。

接口：

```text
GET    /sync/conflicts
POST   /sync/conflicts/:id/resolve
POST   /sync/conflicts/:id/ignore
```

解决冲突时必须：

1. 写最终对象版本。
2. 写 change_log。
3. 标记 conflict resolved。
4. 写 audit_log。
5. 通知其他设备拉取最终结果。

## 7. 同步、离线与冲突规则

### 7.1 推荐冲突策略

不同字段可以有不同策略。

| 字段类型 | 默认策略 |
|---|---|
| 标题、描述、时间 | 冲突候选，人工确认 |
| 完成状态 | 如果一端完成、一端编辑，人工确认 |
| 颜色、排序、折叠状态 | 可采用 last-write-wins，但最好仍可追溯 |
| 删除 vs 修改 | 高风险冲突，必须人工确认 |
| 文件相关字段 | 不自动覆盖，保留双版本 |

### 7.2 删除策略

所有同步对象默认软删除：

```text
deleted_at 不为空
operation = delete
服务端保留 tombstone
客户端拉取 delete change 后本地标记删除
```

不要直接物理删除，否则离线设备无法知道对象被删。

### 7.3 幂等策略

客户端每条 mutation 必须带 `idempotency_key`。

服务端如果收到重复 key：

- 已成功处理过：返回上次结果。
- 正在处理：返回处理中或稍后重试。
- 失败过：根据错误类型决定是否可重试。

## 8. 异常与边界情况

必须考虑：

1. push 成功但客户端没收到响应。
   - 依靠 idempotency_key 避免重复创建。
2. pull 到一半应用失败。
   - 不 ack，下一次重新 pull。
3. 客户端本地数据库损坏。
   - 提供重新从服务端拉取的恢复机制。
4. 服务端变更太多。
   - 分页拉取，不阻塞 UI。
5. 同一个对象被删除后又修改。
   - 进入删除/修改冲突。
6. 设备时间不准。
   - 版本以服务端 version/change_id 为准，不完全依赖客户端时间。
7. Token 失效。
   - 同步暂停，提示重新登录，不删除本地队列。
8. 用户长期离线。
   - 恢复后先 pull 再 push，或 push 时严格基于 baseVersion 判断冲突。

## 9. 安全与隐私

同步层本身不应该把敏感内容随意扩散。

规则：

- 原始键鼠输入、位置轨迹、聊天内容属于高敏感数据。
- 高敏感对象默认不自动同步，或者需要单独开关。
- 同步日志不要记录完整敏感 payload，只记录对象类型、字段名、错误信息。
- 管理端查看敏感数据时要有权限和审计。
- AI 不应直接读取 offline_mutations 里的完整敏感 payload。

## 10. 验收标准

### `[B] 骨架完成`

满足：

- 有 offline_mutations。
- 有 sync_object_states。
- 有 /sync/push、/sync/pull、/sync/ack、/sync/conflicts。
- 有基础设备状态。
- 有最小冲突表。

### `[M] MVP 可用`

必须实测：

- 断网创建任务，本地可见。
- 恢复网络后任务同步到服务端。
- 第二设备能拉取任务。
- 同步失败时本地队列不丢。
- UI 能看到同步状态。

### `[V] 已验证可用`

必须实测：

- 两设备同时修改同一任务，产生冲突。
- 用户能处理冲突。
- 处理后两端一致。
- 删除/修改冲突能正确处理。
- push 成功但客户端断连不会重复创建。
- 大批量数据分页同步正常。

### `[S] 稳定可用`

必须具备：

- 自动化测试覆盖 push/pull/conflict/idempotency。
- 真实使用至少一段时间没有严重数据丢失。
- 有同步诊断页。
- 有日志和错误恢复方案。
- 有数据库备份和恢复说明。
