# 第二部分：F 活动理解与实际记录

## 1. 目标

活动理解与实际记录是 FlowPlan 区别于普通日程/待办软件的核心模块。

它的目标不是“记录很多日志”，而是把 Windows、Android、键鼠输入、软件活动、文件路径、日程、任务等杂乱信息，整理成用户能看懂、系统能利用的事实。

核心目标：

```text
原始活动记录
  -> 清洗和合并
  -> 活动片段
  -> 活动理解
  -> 任务实际投入
  -> 实际记录候选
  -> 用户确认
  -> 日报、排程、复盘可用的事实
```

最终用户应该看到的不是：

```text
10:01:23 VS Code
10:01:41 资源管理器
10:02:08 Chrome
10:03:11 VS Code
10:04:02 PyCharm
```

而是：

```text
10:00 - 11:20 可能在完成《数据库课程作业》
证据：VS Code、PyCharm、项目文件夹、浏览器搜索、任务标题匹配
置信度：82%
建议：计入任务“数据库课程作业”的实际投入 1 小时 20 分钟
```

---

## 2. 用户流程

### 2.1 自动整理一天活动

```text
用户打开“今日回顾”或“活动理解”页面
  -> 系统读取当天原始活动记录
  -> 自动合并成若干活动片段
  -> 对每个片段生成标题、时间、证据、置信度
  -> 尝试关联任务/日程/文件夹
  -> 高置信度片段可作为任务实际投入候选
  -> 低置信度片段等待用户确认或修正
```

用户看到的是类似：

```text
09:50 - 10:35 上课：高等数学
来源：日程阻挡时间 + 手机低输入 + 位置可能在教学楼
置信度：90%
操作：确认 / 修改 / 忽略

10:50 - 12:15 完成数据库课程作业
来源：VS Code、PyCharm、数据库作业文件夹、任务标题匹配
置信度：82%
操作：确认计入任务 / 改为其他任务 / 拆分 / 忽略

12:15 - 12:40 休息或用餐
来源：手机应用切换频繁，电脑无活动
置信度：65%
操作：确认 / 修改
```

### 2.2 用户确认实际记录

```text
系统生成候选实际记录
  -> 用户点击确认
  -> 写入 actual_activity_logs
  -> 关联 task_work_logs
  -> 写入审计
  -> 日报、周报、排程可读取
```

确认后，这段时间才成为“正式事实”。

### 2.3 用户修正错误推断

```text
系统认为 10:50 - 12:15 是“数据库课程作业”
用户改成“软件工程小组项目”
  -> 保存修正
  -> 更新该片段关联任务
  -> 写入用户修正规则
  -> 后续相同文件夹/窗口标题优先匹配软件工程项目
```

修正不能只是改一次，而应该沉淀成规则。

### 2.4 拆分片段

场景：系统把 9:00 - 11:00 合并成一个片段，但用户实际 9:00 - 10:00 写作业，10:00 - 11:00 开会。

流程：

```text
用户点击“拆分”
  -> 选择拆分时间点
  -> 系统生成两个片段
  -> 用户分别确认活动类型和任务关联
  -> 写入审计
```

### 2.5 合并片段

场景：系统把一次连续写作业切成了 5 段。

流程：

```text
用户多选片段
  -> 点击合并
  -> 系统保留所有证据
  -> 重新计算时间范围和置信度
  -> 用户确认标题和任务关联
```

## 3. 数据模型

### 3.1 原始活动层

这些表是证据，不一定直接给用户看。

#### `raw_activity_logs`

记录窗口、应用、进程等原始事件。

建议字段：

```text
id
user_id
device_id
platform              windows / android
started_at
ended_at
app_name
process_name
window_title
window_url
file_path
project_path
activity_type_hint    coding / browser / document / chat / video / unknown
source                windows_foreground / android_usage / manual_import
sensitive_level       low / medium / high
created_at
```

#### `tracked_input_events`

记录输入统计，不建议默认保存完整输入内容。

```text
id
user_id
device_id
started_at
ended_at
keyboard_count
mouse_click_count
mouse_move_distance
active_seconds
input_density         low / medium / high
contains_raw_text     true / false
sensitive_level       medium / high
created_at
```

原则：

- 默认只保存输入数量、节奏、活跃程度。
- 不默认保存完整键盘输入原文。
- 如果本地确实保存原文，必须标记为 high sensitive，默认不上传第三方 AI。

---

### 3.2 活动片段层

#### `activity_segments`

把连续杂乱记录合并后的片段。

```text

device_ids_json
started_at
ended_at
duration_seconds
primary_app
primary_window_title
primary_file_path
primary_project_path
segment_type          work / study / class / meeting / rest / entertainment / communication / unknown
merge_method          rule / model / manual
confidence            0-100
status                candidate / confirmed / rejected / split / merged
created_at
updated_at
```

#### `activity_segment_evidence`

记录片段的证据来源。

```text

```

这样用户可以看到“为什么系统这么判断”。

### 3.3 活动理解层

#### `activity_interpretations`

对片段的自然语言解释。

```text
id
segment_id
title
summary
interpreted_type      coding / writing / reading / class / meeting / rest / communication / unknown
matched_task_id
matched_event_id
matched_folder_id
confidence
reason_json

created_at

```

`reason_json` 示例：

```json
{
  "matchedKeywords": ["数据库", "作业"],
  "matchedApps": ["VS Code", "PyCharm"],
  "matchedPaths": ["D:/courses/database/homework"],
  "matchedTask": "数据库课程作业",
  "timeOverlap": "任务截止前 1 天",
  "negativeSignals": ["中途短暂打开微信 2 分钟"]
}
```

### 3.4 任务实际投入层

#### `task_work_logs`

记录某个任务实际投入了多少时间。

```text
id
user_id
task_id
segment_id
actual_log_id
started_at
ended_at
duration_seconds
confidence
source_type           activity_segment / manual / calendar_block / ai_draft
status                candidate / confirmed / rejected
created_at
confirmed_at
```

原则：

- 高置信度可以先作为候选显示在任务详情中。
- 只有用户确认后，才作为正式实际投入。
- 排程可以读取候选，但要区分“已确认”和“推断”。

### 3.5 实际记录层

#### `actual_activity_logs`

最终事实记录。

```text
id
user_id
title
started_at
ended_at
duration_seconds
source_type           manual / calendar_block / activity_inference / ai_draft
source_id
confidence
status                candidate / confirmed / rejected / merged

created_at
confirmed_at
```

实际记录的定位：

- 日程/任务是计划。
- 原始追踪是证据。
- 实际记录是最终事实。

## 5. 活动片段构建规则

### 5.1 基础合并规则

按时间排序原始记录后合并。

推荐规则：

| 情况 | 处理 |
|---|---|
| 同一 app / 同一窗口连续活动 | 合并 |
| VS Code + 终端 + 浏览器开发文档 + 项目文件夹 | 倾向合并为开发活动 |
| Word + PDF + 浏览器资料 + 同一课程文件夹 | 倾向合并为写作/学习活动 |
| 微信/QQ/浏览器短暂打开 1-3 分钟 | 不一定打断主活动 |
| 连续无输入超过 10-15 分钟 | 可切断或标记为空闲 |
| 电脑无活动但手机高频使用 | 可能切换为手机活动 |
| 日程阻挡时间覆盖且追踪证据不冲突 | 倾向生成日程实际候选 |

### 5.2 短干扰容忍

比如写作业时短暂打开微信：

```text
10:00 - 10:25 VS Code
10:25 - 10:27 微信
10:27 - 10:50 VS Code
```

不应该切成三段，而应该生成：

```text
10:00 - 10:50 写代码/写作业
证据中标记：中途短暂通信 2 分钟
```

### 5.3 活动切断条件

建议切断条件：

- 主应用类型明显变化，例如 VS Code -> Bilibili 长时间播放。
- 空闲超过阈值，例如 15 分钟。
- 日程边界强切断，例如 10:00 开始上课。
- 文件项目路径变化明显。
- 用户手动拆分。

### 5.4 多设备合并

同一时间段可能有 Windows 和 Android 数据。

规则：

| 情况 | 解释 |
|---|---|
| Windows 高输入，Android 少量通知 | 以 Windows 活动为主 |
| Windows 无输入，Android 高使用 | 以 Android 活动为主 |
| 两端都有高活动 | 可能多任务，或手机辅助电脑工作，需要降低置信度 |
| Android 只是音乐/后台 | 不作为主活动 |

## 6. 任务匹配规则

### 6.1 匹配信号

任务匹配不能只靠标题关键词，应综合：

| 信号 | 示例 | 权重建议 |
|---|---|---|
| 任务标题关键词 | “数据库作业”匹配窗口标题/文件路径 | 高 |
| 文件夹绑定 | 任务绑定 `database/homework` 文件夹 | 很高 |
| 最近打开文件 | 最近打开作业文档或项目代码 | 高 |
| 日程时间重叠 | 正在某门课时间段 | 中高 |
| 截止时间接近 | 明天截止的任务更可能被做 | 中 |
| 应用类型 | VS Code 对编程任务，Word 对写作任务 | 中 |
| 用户历史修正 | 之前用户把该路径修正为某任务 | 很高 |
| 输入密度 | 高输入更像写作/编码，低输入更像阅读/视频 | 中 |

### 6.2 置信度计算

建议先用规则分数，不急着训练模型。

示例：

```text
基础分：0
任务标题命中：+25
绑定文件夹命中：+35
窗口标题命中：+15
应用类型匹配：+10
截止时间接近：+5
短暂干扰：-5
多个任务同时匹配：-15
最终限制到 0-100
```

置信度解释：

| 分数 | 处理 |
|---|---|
| 85-100 | 高置信度，可推荐直接确认 |
| 65-84 | 中置信度，作为候选，需要用户确认 |
| 40-64 | 低置信度，只显示“可能相关” |
| 0-39 | 不自动关联任务 |

## 7. LLM 的使用边界

LLM 不应该实时分析每个窗口切换。

推荐方式：

```text
原始数据
  -> 本地/服务端规则先合并成片段
  -> 去除敏感内容
  -> 只把片段摘要发给 LLM
  -> LLM 生成自然语言解释或候选标题
  -> 写入 activity_interpretations
  -> 用户可确认或修正
```

### 7.1 可以发给 LLM 的内容

- 应用名。
- 脱敏后的窗口标题。
- 文件夹名称或项目名摘要。
- 任务标题和描述摘要。
- 日程标题。
- 时间范围。
- 输入强度统计。

### 7.2 默认不能发给 LLM 的内容

- 完整键盘输入原文。
- 私密聊天内容。
- 完整文件内容。
- 精确位置轨迹。
- 未脱敏 URL 中的 token、账号、查询参数。
- 高敏感窗口标题，例如密码、支付、医疗等。

### 7.3 LLM 输出限制

LLM 只能输出：

- 片段标题建议。
- 活动类型建议。
- 任务关联建议。
- 解释文本。
- 置信度辅助判断。

LLM 不能直接：

- 写入实际记录。
- 修改任务实际投入。
- 删除原始记录。
- 修改排程。

这些都必须走候选和确认。

## 10. 同步、离线与冲突

活动理解涉及三类数据：

1. 原始追踪数据。
2. 派生理解结果。
3. 用户确认后的事实。

### 10.1 推荐同步策略

| 数据 | 是否同步 | 说明 |
|---|---|---|
| 原始窗口记录 | 可选同步 | 默认可只同步摘要，完整原始数据需开关 |
| 输入统计 | 可同步 | 只同步数量和强度，不同步原文 |
| 键盘输入原文 | 默认不同步 | 高敏感，只能本地保存或用户明确开启 |
| 活动片段 | 同步 | 属于派生摘要 |
| 活动解释 | 同步 | 用于多端查看和日报 |
| 任务实际投入 | 同步 | 影响排程和报告 |
| 实际记录 | 同步 | 属于核心事实 |
| 用户修正规则 | 同步 | 用于多端一致理解 |

### 10.2 冲突场景

| 场景 | 处理 |
|---|---|
| 两端都修改同一片段标题 | 生成冲突 |
| 一端确认，一端拒绝 | 生成冲突 |
| 一端拆分，一端合并 | 高风险冲突，人工处理 |
| 一端删除原始记录，一端生成解释 | 保留解释，但标记证据缺失 |
| 用户修改任务关联后，模型又重新推断 | 用户修正优先 |

## 11. 异常与边界情况

必须考虑：

1. 原始记录太碎。
   - 需要短切换合并规则。
2. 原始记录太少。
   - 降低置信度，不要强行推断。
3. 同时使用电脑和手机。
   - 多设备证据合并，必要时显示不确定。
4. 窗口标题包含隐私。
   - 脱敏或不展示完整标题。
5. 文件路径失效。
   - 仍保留历史证据，但提示路径不可访问。
6. 日程和追踪冲突。
   - 例如计划上课，但电脑在打游戏，生成偏离候选。
7. 用户长期不确认候选。
   - 候选可以用于弱参考，但不能变成事实。
8. LLM 输出错误。
   - 只作为建议，不能直接写事实。
9. 任务改名或删除。
   - 历史实际投入仍保留当时关联，并提示任务已变化。

## 12. 安全与隐私

活动追踪是 FlowPlan 里最敏感的模块之一。

必须遵守：

- 默认不把键盘输入原文发给第三方 AI。
- 默认不把聊天内容发给第三方 AI。
- 默认不把完整文件内容发给第三方 AI。
- 原始活动日志可设置保留周期，例如 7 天、30 天、90 天。
- 用户可以开启“隐私暂停模式”。
- 用户可以指定忽略应用，例如微信、QQ、银行、浏览器无痕窗口。
- 日报和 AI 只使用脱敏摘要。
- 管理端查看敏感记录必须写审计。

## 13. 验收标准

### `[B] 骨架完成`

满足：

- 有 `activity_segments`。
- 有 `activity_interpretations`。
- 有 `task_work_logs`。
- 有 `actual_activity_logs`。
- 有基础生成接口。
- 有基础确认/拒绝接口。

### `[M] MVP 可用`

必须实测：

- 用一天真实 Windows 活动记录生成活动片段。
- 片段数量大致可读，例如 5-20 个，而不是几百条。
- 每个片段有标题、时间、证据、置信度。
- 用户可以确认一个片段为实际记录。
- 用户可以把一个片段关联到任务。
- 任务详情能看到实际投入候选或已确认投入。

### `[V] 已验证可用`

必须实测：

- 连续多天数据都能生成较合理活动片段。
- 用户修正后，同类情况下一次更准确。
- 日程阻挡时间能生成实际记录候选。
- 活动片段能影响排程剩余时间。
- 日报能引用活动片段证据。
- 低置信度不会静默写成事实。

### `[S] 稳定可用`

必须具备：

- 大量原始记录下性能可接受。
- 有后台任务和进度显示。
- 有隐私暂停和忽略应用。
- 有脱敏测试。
- 有规则回归测试。
- 有 LLM 调用失败 fallback。
- 至少经过多周真实使用修正。
