# 第三部分：G 智能排程

## 1. 目标

智能排程的目标不是简单地把任务塞进空白时间，而是根据“计划、实际进展、剩余时间、截止时间、阻挡日程、用户习惯和风险”生成可解释、可确认、可回滚的排程草案。

核心目标：

```text
计划应该做什么
  + 实际已经做了什么
  + 还有多少没做
  + 哪些时间不能动
  + 哪些任务快截止
  + 用户当前偏离了多少
  -> 生成排程草案
  -> 解释为什么这样排
  -> 用户确认
  -> 写入排程片段
  -> 影响后续日报和复盘
```

智能排程必须遵守：

1. 不静默写入最终排程。
2. 先生成草案，用户确认后才写入。
3. 固定日程和阻挡日程优先级最高。
4. 已确认实际投入会减少任务剩余时间。
5. 候选实际投入可以作为弱参考，但必须标注不确定。
6. 每个安排都要能解释。
7. 未排任务也要说明原因。
8. 用户拒绝、修改、部分接受都要记录。

## 2. 用户流程

### 2.1 普通自动排程流程

```text
用户打开“智能排程”
  -> 选择排程范围：今天 / 明天 / 本周 / 自定义
  -> 系统读取任务、日程、排程片段、实际投入
  -> 系统生成排程草案
  -> 用户看到每个任务被安排到哪里、为什么这样安排
  -> 用户确认 / 修改 / 拒绝
  -> 确认后写入 task_schedule_segments
  -> 写入审计和同步队列
```

用户看到的不是“已经帮你排好了”，而是：

```text
排程草案：今晚 19:30 - 21:00 数据库课程作业
原因：
- 明天 23:59 截止
- 预计还剩 1.5 小时
- 今天下午已投入 40 分钟
- 19:30 后没有阻挡日程
- 该任务优先级高

操作：确认 / 修改时间 / 换任务 / 拒绝本次建议
```

### 2.2 计划偏离后的重排流程

场景：用户原计划 19:00 写作业，但实际 19:00 - 20:00 在看视频。

```text
系统检测到当前实际活动与计划不符
  -> 标记计划偏离
  -> 计算受影响任务
  -> 生成重排草案
  -> 显示原计划与新计划对比
  -> 用户确认或拒绝
```

展示示例：

```text
检测到计划偏离：
原计划：19:00 - 20:30 数据库课程作业
实际：19:00 - 20:00 娱乐/视频，置信度 78%
影响：数据库课程作业预计还剩 1.5 小时，明天截止

建议：
- 今晚 20:30 - 22:00 补上数据库课程作业
- 将“英语阅读”推迟到明天 08:30

操作：接受重排 / 只接受第一项 / 手动调整 / 忽略
```

### 2.3 用户部分接受草案

智能排程不能要求用户全盘接受。

```text
系统生成 5 个排程建议
用户接受 3 个，修改 1 个，拒绝 1 个
  -> 接受的写入排程片段
  -> 修改的按用户改后写入
  -> 拒绝的记录原因
  -> 未接受部分不写库
```

### 2.4 草案过期流程

如果用户生成草案后又修改了任务或日程，草案不能继续无脑应用。

```text
用户生成排程草案
  -> 过了 30 分钟
  -> 用户新增一个会议
  -> 系统提示草案已过期
  -> 需要重新生成或重新校验
```

## 4. 排程输入

智能排程必须显式读取这些输入。

### 4.1 硬约束

硬约束不能轻易违反。

| 输入 | 说明 |
|---|---|
| 阻挡日程 | 上课、考试、会议、不可移动时间 |
| 已锁定排程片段 | 用户手动锁定，不允许自动移动 |
| 任务截止时间 | 截止前必须尽量安排 |
| 用户睡眠/不可用时间 | 夜间、通勤等不可安排或弱安排 |
| 外部日历占用 | Outlook/系统日历中的忙碌时间 |

### 4.2 软约束

软约束用于排序和解释。

| 输入 | 说明 |
|---|---|
| 任务优先级 | 高优先级优先安排 |
| 预计耗时 | 决定需要多少时间块 |
| 已确认实际投入 | 减少剩余时间 |
| 候选实际投入 | 作为弱参考，降低置信度 |
| 用户习惯 | 例如晚上写代码，早上背单词 |
| 文件上下文 | 需要电脑、需要某资料文件夹 |
| 最近拖延情况 | 多次偏离的任务提高风险 |
| 任务能否切分 | 大任务可分块，小任务一次完成 |
| 能量需求 | 高脑力任务不安排到低能量时段 |

### 4.3 派生输入

排程前需要先计算：

```text
任务剩余时间 = 预计总耗时 - 已确认实际投入 - 可接受候选投入
任务紧迫度 = 截止时间距离 + 剩余时间 + 优先级
计划偏离程度 = 原计划时间 - 实际完成时间
可用时间块 = 时间范围 - 阻挡日程 - 已锁定片段 - 不可用时间
风险等级 = 是否可能来不及 + 偏离次数 + 剩余时间
```

## 5. 排程算法建议

不要一开始做复杂约束求解器。先用规则 + 可解释打分，后续再升级。

### 5.1 第一版算法：规则打分 + 贪心填充

流程：

```text
1. 收集排程范围内所有可用时间块。
2. 收集需要安排的任务。
3. 计算每个任务剩余时间。
4. 给任务计算优先级分数。
5. 按分数排序任务。
6. 对每个任务寻找合适时间块。
7. 生成草案项。
8. 对未排任务生成未排原因。
9. 输出解释和风险。
```

### 5.2 任务优先级分数

示例：

```text
score = 0
截止在 24 小时内：+50
截止在 3 天内：+30
priority = urgent：+40
priority = high：+25
剩余时间 > 今日可用时间 50%：+20
最近偏离过：+15
用户手动置顶：+30
任务已开始但未完成：+10
没有估时：-10
需要特定文件但当前设备不可用：-20
```

### 5.3 时间块匹配分数

```text
score = 0
时间块长度足够：+30
匹配用户偏好时间：+15
匹配任务能量需求：+10
任务需要电脑且当前是电脑端：+15
距离截止更近：+10
紧接同类任务太久：-10
时间块太碎：-5
晚上太晚安排高脑力任务：-15
```

### 5.4 切分策略

| 任务类型 | 策略 |
|---|---|
| 小任务 < 30 分钟 | 尽量一次完成 |
| 中任务 30-120 分钟 | 可安排 1-2 个块 |
| 大任务 > 120 分钟 | 分块安排，优先较早开始 |
| 高脑力任务 | 避免太晚或碎片时间 |
| 复习/背诵 | 可安排碎片时间 |

### 5.5 未排原因

未排任务必须给出原因，不能只是不显示。

示例：

```text
未排：英语阅读
原因：今天剩余可用时间不足；数据库课程作业明天截止且优先级更高。
建议：明早 08:00 后重新安排，或延长今晚可用时间。
```

### 6.1 排程草案

每条草案必须包含：

```text
任务
建议开始时间
建议结束时间
```

### 6.2 解释文本

解释不能只是技术字段，要给用户看得懂：

```text
把“数据库课程作业”安排在今晚 20:30，是因为它明天截止，预计还剩 90 分钟，且你今晚 20:30 后没有阻挡日程。
```

### 6.3 风险提醒

```text

```

### 6.4 变更对比

重排时必须显示：

| 原安排 | 新安排 | 变化原因 |
|---|---|---|
| 19:00-20:30 数据库作业 | 20:30-22:00 数据库作业 | 原计划时间已偏离 |
| 20:30-21:00 英语阅读 | 明早 08:30-09:00 | 数据库作业更紧急 |

## 10. 同步、离线与冲突

### 10.1 哪些数据要同步

| 数据 | 同步策略 |
|---|---|
| 已确认排程片段 | 必须同步 |
| 排程草案 | 建议同步，便于多端查看 |
| 用户接受/拒绝记录 | 必须同步 |
| 计划偏离记录 | 建议同步 |
| 输入快照 | 可同步摘要，不同步高敏感原始活动 |
| 排程解释 | 同步 |

### 10.2 冲突场景

| 场景 | 处理 |
|---|---|
| 两端同时生成不同排程草案 | 两个草案并存，用户选择 |
| 草案生成后任务被修改 | 草案标记过期 |
| 一端确认排程，一端删除任务 | 高风险冲突，人工确认 |
| 用户手动移动已确认片段，系统又重排 | 用户手动优先，系统重新计算 |
| Outlook 外部日历新增占用，影响已确认片段 | 生成冲突/风险提醒，不静默移动 |

### 10.3 离线规则

- 离线时可以基于本地数据生成草案。
- 离线草案必须标注“基于本地数据，可能不是最新”。
- 确认后写入本地排程片段和离线队列。
- 联网后若发现服务端已有冲突，进入同步冲突处理。

## 11. 异常与边界情况

必须考虑：

1. 任务没有预计耗时。
   - 不能直接忽略，应提示用户补估时，或使用默认值。
2. 任务截止时间为空。
   - 按优先级和用户偏好安排，但风险较低。
3. 可用时间不足。
   - 明确未排原因和风险。
4. 已有排程片段重叠。
   - 生成冲突提示，不直接覆盖。
5. 用户锁定某个片段。
   - 自动排程不得移动。
6. 草案生成后数据变化。
   - 草案过期或重新校验。
7. 实际投入超过预计耗时。
   - 任务可能已完成，建议确认完成或调整估时。
8. 阻挡日程和任务重叠。
   - 阻挡日程优先。
9. 跨天任务。
   - 支持拆分，不要强行安排到一天。
10. 同步失败。
   - 本地保留，显示等待同步。

## 12. 安全与隐私

排程本身不一定高敏感，但它会读取活动理解、实际记录、文件上下文，间接涉及隐私。

规则：

- 排程输入快照不要包含完整键盘输入原文。
- 排程解释不要暴露过度敏感窗口标题。
- AI 参与排程时，只发送摘要和必要字段。
- 写入 Outlook 或外部日历必须二次确认。
- 删除或移动大量排程片段必须二次确认。
- 用户拒绝排程的理由可以记录，但应允许不填写。

## 13. 验收标准

### `[B] 骨架完成`

满足：

- 有排程引擎。
- 能读取任务、日程、阻挡时间。
- 能生成 placement。
- 能生成解释或未排原因。
- 有排程片段持久化基础。

### `[M] MVP 可用`

必须实测：

- 用户创建多个任务和阻挡日程。
- 系统生成排程草案。
- 草案显示时间、任务、原因、未排原因。
- 用户拒绝草案时不写库。
- 用户确认草案后写入排程片段。
- 已确认实际投入会减少剩余时间。

### `[V] 已验证可用`

必须实测：

- 真实计划偏离后生成重排草案。
- 原计划和新计划能对比。
- 用户可以部分接受。
- 草案过期能被检测。
- 锁定片段不会被移动。
- 阻挡日程不会被覆盖。
- 排程结果能同步到另一设备。

### `[S] 稳定可用`

必须具备：

- 有排程规则测试。
- 有复杂边界测试：跨天、重叠、无估时、截止冲突。
- 有排程运行日志和调试页面。
- 有用户反馈闭环。
- 真实使用多周后不会频繁生成明显荒谬安排。
