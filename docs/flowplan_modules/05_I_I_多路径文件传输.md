# 第五部分：I 多路径文件传输

## 1. 目标

I 模块的目标是建立 FlowPlan 的“多路径文件传输引擎”。

它不是简单的“上传到服务器”，也不是 H 文件中心里的“打开文件”。它要解决的是：当用户需要在设备之间、设备与服务器之间、服务器与云文件后端之间传输文件时，系统如何选择最合适的路径，并保证传输可靠、可续传、可校验、可追溯。

核心目标：

```text
文件传输请求
  -> 判断文件大小
  -> 判断文件位置
  -> 判断目标设备
  -> 判断网络环境
  -> 选择最优传输路径
  -> 小文件整包传输
  -> 中大文件分块传输
  -> 上传和下载都支持断点续传
  -> 失败后自动降级或等待重试
  -> 完成后校验 hash
  -> 写入传输记录和审计
```

最终用户应该感受到：

1. 小文件传得快。
2. 大文件不会因为中断就重来。
3. 同一局域网时尽量不绕服务器。
4. 校园网同 WiFi 但互相发现不了时，能借助服务端辅助发现。
5. 跨网络时尽量 P2P，失败后再走服务器中转。
6. 传输过程有进度、速度、剩余时间、失败原因。
7. 文件传完后能确认没有损坏。
8. 冲突不会静默覆盖。

一句话目标：

```text
优先直连，失败降级；小文件简单，大文件可靠；中断可续，完成可验。
```

## 3. 用户流程

### 3.1 小文件从 Windows 传到 Android

```text
用户在 Windows 文件中心选择文件
  -> 点击“发送到手机”
  -> 系统发现 Android 设备在线
  -> 检查文件大小小于小文件阈值
  -> 检查双方是否局域网可达
  -> 如果可达，局域网直连发送
  -> 如果不可达，尝试 P2P
  -> P2P 失败，走服务端中转
  -> Android 收到后保存到对应资料库目录
  -> 写入 file_transfer_sessions
  -> 更新文件中心元数据
```

用户看到：

```text
正在发送 report.md 到 Android 手机
路径：局域网直连
大小：8.4 MB
进度：100%
状态：已完成，校验通过
```

### 3.2 大文件上传到服务端

```text
用户选择一个 2GB 视频或压缩包
  -> 系统判断为大文件
  -> 创建上传会话
  -> 按 8MB 或 16MB 分块
  -> 逐块上传
  -> 记录每个 chunk 状态
  -> 网络中断
  -> 会话保留
  -> 网络恢复后查询缺失 chunk
  -> 只补传缺失部分
  -> 完成后服务端合并或登记对象
  -> 校验整体 hash
```

用户看到：

```text
上传暂停：网络中断
已完成：63%
已上传：1.26GB / 2.00GB
恢复后将继续上传，不会重传已完成部分
```

### 3.3 大文件从服务端下载到本地

```text
用户在文件中心点击云端文件
  -> 本地不存在
  -> 系统提示是否下载
  -> 创建下载会话
  -> 使用 Range 或 chunk 下载
  -> 写入临时文件
  -> 中断后保留已下载分块
  -> 恢复时继续下载缺失范围
  -> 完成后校验 hash
  -> 移动到最终路径
  -> 更新 file_node_device_locations
```

### 3.4 同 WiFi 但无法广播发现

这是你之前特别强调的校园网场景。

```text
两台设备连接同一个 WiFi 名称
  -> 传统局域网广播发现失败
  -> 客户端把当前 WiFi SSID、局域网 IP、端口候选上报服务端
  -> 服务端只做 rendezvous，不承载文件内容
  -> 双方互相拿到候选地址
  -> 尝试直接 TCP/HTTP 连接
  -> 成功则局域网传输
  -> 失败则继续尝试 P2P 或服务端中转
```

注意：

- SSID 只能作为辅助信号，不代表一定在同一可达网络。
- IP 候选需要过期时间。
- 不能把同 WiFi 当成安全认证依据，仍要设备身份和一次性传输 token。

### 3.5 P2P 失败后服务端中转

```text
设备 A 想给设备 B 传文件
  -> 尝试局域网失败
  -> 尝试 WebRTC P2P
  -> STUN 能发现候选但连接失败
  -> TURN 不可用或成本太高
  -> 降级为服务端中转
  -> A 上传到服务端临时对象
  -> B 从服务端断点下载
  -> 到期后服务端清理临时对象
```

用户看到的应该是：

```text
直连失败，已切换为服务器中转。速度可能较慢，但支持断点续传。
```

## 4. 传输路径优先级

推荐路径优先级：

```text
0. 目标设备本地已有文件，直接打开
1. 同设备本地复制或移动
2. 局域网直连
3. 同 WiFi 服务端辅助发现后直连
4. WebRTC P2P 直连
5. TURN 中继
6. FlowPlan 服务端中转
7. OneDrive / 云端后端下载
```

### 4.1 首版实现顺序

不要一开始就做完整 P2P。

建议顺序：

```text
第一阶段：服务端中转 + 分块 + 断点续传
第二阶段：局域网直连
第三阶段：同 WiFi 辅助发现
第四阶段：WebRTC P2P
第五阶段：TURN 中继
第六阶段：云端后端策略优化
```

原因：

- 服务端中转最容易做成稳定闭环。
- 局域网直连收益高，复杂度适中。
- P2P/NAT 穿透复杂度高，不应该阻塞前期 MVP。
- TURN 中继需要额外服务器和带宽成本，不应默认依赖。

## 5. 文件大小策略

### 5.1 默认阈值

建议默认值：

| 类型 | 大小 | 策略 |
|---|---|---|
| 极小文件 | 小于 1MB | 可直接整包传输，内存读取可接受 |
| 小文件 | 1MB - 32MB | 整包或少量分块，优先简单快速 |
| 中等文件 | 32MB - 1GB | 必须分块，支持暂停和续传 |
| 大文件 | 1GB 以上 | 必须分块，必须断点续传，必须 hash 校验 |
| 超大文件 | 10GB 以上 | 需要提示风险，建议仅在局域网或稳定网络下传输 |

这些阈值应进入远程配置或本地设置，后续可调整。

### 5.2 分块大小

建议：

| 网络/场景 | 分块大小 |
|---|---|
| 移动网络 | 2MB - 4MB |
| 普通 WiFi | 4MB - 8MB |
| 局域网 | 8MB - 32MB |
| 服务端对象存储 | 8MB - 64MB，按后端要求调整 |

首版可以固定 8MB，后续再动态调整。

## 6. 可复用方案和外部软件

### 6.1 断点上传

推荐参考 tus 协议。

tus 是基于 HTTP 的可恢复上传协议，目标就是让上传中断后可以继续，而不需要重传已经完成的部分。

首版可以不完整实现 tus 标准，但建议借鉴它的模型：

```text
创建上传资源
记录 upload offset
客户端查询 offset
从 offset 继续上传
服务端校验并更新 offset
```

如果以后想少造轮子，可以评估直接接入 tusd 作为上传服务。

### 6.2 断点下载

推荐使用 HTTP Range 思路。

客户端请求某个字节范围：

```text
Range: bytes=1048576-2097151
```

服务端返回局部内容，客户端写入临时文件对应位置。

适合：

- 暂停/恢复下载。
- 大文件分段下载。
- 下载失败后只补缺失部分。

### 6.3 对象存储分片

服务端最终不建议把文件块长期放 PostgreSQL。

推荐：

```text
开发期：本机目录或 MinIO
生产期：S3 兼容对象存储，例如 MinIO / S3
```

S3 multipart upload 的思路是把一个对象拆成多个 part 独立上传，失败时只重传失败 part，最后由服务端合并或完成对象。

### 6.4 P2P 传输

推荐长期使用 WebRTC DataChannel。

WebRTC DataChannel 可以在两个 peer 之间传输任意数据，适合跨网络 P2P 文件块传输。

FlowPlan 需要的不是音视频，而是数据通道：

```text
signaling 由 FlowPlan Server 提供
候选地址由 STUN/TURN 发现
文件块通过 DataChannel 传输
```

Flutter 端可以评估 `flutter_webrtc`，但 P2P 不应作为 MVP 的阻塞项。

### 6.5 STUN/TURN

推荐自建或后续部署 coturn。

STUN 用于发现 NAT 后的候选地址。
TURN 用于直连失败时中继流量。

注意：

- TURN 会消耗服务器带宽。
- TURN 更接近“专门的 P2P 中继”，不等同于 FlowPlan 普通文件服务端中转。
- 首版可以先不启用 TURN，只做服务端中转兜底。

### 6.6 Syncthing / Tailscale 的边界

Syncthing 和 Tailscale 都值得参考，但不建议首版深度依赖。

可参考：

- Syncthing 的设备、文件夹、同步状态设计。
- Tailscale 的虚拟局域网思路。

不建议：

- 一开始要求用户额外安装复杂依赖。
- 把 FlowPlan 核心传输完全绑定到某个第三方同步软件。

### 8.1 API 设计

#### 创建传输会话

```text
POST /file-transfer/sessions
```

输入：

```json
{
  "sourceNodeId": "...",
  "targetDeviceId": "...",
  "targetRootId": "...",
  "fileName": "report.md",
  "fileSizeBytes": 12345678,
  "checksumSha256": "...",
  "preferredStrategy": "auto"
}
```

输出：

```json
{
  "sessionId": "...",
  "chunkSizeBytes": 8388608,
  "totalChunks": 2,
  "status": "pending"
}
```

#### 上报设备网络候选

```text
POST /file-transfer/presence
```

输入：

```json
{
  "deviceId": "...",
  "networkType": "wifi",
  "wifiSsidHash": "...",
  "localIp": "192.168.1.23",
  "localPort": 49152,
  "capabilities": ["lan_http", "server_relay"]
}
```

#### 获取传输候选路径

```text
GET /file-transfer/sessions/:id/candidates
```

#### 选择传输策略

```text
POST /file-transfer/sessions/:id/select-strategy
```

#### 上传 chunk 到服务端中转

```text
PUT /file-transfer/sessions/:id/chunks/:chunkIndex
```

#### 查询缺失 chunk

```text
GET /file-transfer/sessions/:id/missing-chunks
```

#### 完成上传

```text
POST /file-transfer/sessions/:id/complete
```

#### 下载 chunk 或 Range

```text
GET /file-transfer/sessions/:id/chunks/:chunkIndex
GET /file-transfer/objects/:objectId/range
```

#### 暂停、恢复、取消

```text
POST /file-transfer/sessions/:id/pause
POST /file-transfer/sessions/:id/resume
POST /file-transfer/sessions/:id/cancel
```

### 8.2 服务端中转存储

首版推荐：

```text
开发期：server_storage/tmp_transfers/session_id/chunk_index.part
后续：MinIO/S3 multipart 或对象存储临时对象
```

注意：

- 临时 chunk 不应长期保留。
- completed 后要清理临时 chunk。
- failed/expired 会话要由后台任务清理。
- 服务端不要把大文件块存 PostgreSQL。

### 8.3 后台清理任务

需要定期清理：

```text
过期传输会话
未完成临时 chunk
已完成但超过保留期的 relay 文件
失败过多的会话
孤儿 chunk
```

```text
    transfer_error_panel.dart
```

### 9.1 传输引擎职责

`TransferEngine` 负责：

```text
createSession()
probeStrategies()
selectBestStrategy()
startTransfer()
pauseTransfer()
resumeTransfer()
cancelTransfer()
retryFailedChunks()
verifyChecksum()
```

### 9.2 策略选择器

`TransferStrategySelector` 根据：

```text
文件大小
源文件位置
目标设备是否在线
是否同设备
是否同局域网
是否同 WiFi
服务端是否可用
P2P 是否可用
用户设置
```

选择传输路径。

### 9.3 本地分块读写

必须避免一次性把大文件读入内存。

```text
File.openRead(start, end)
  -> 读取 chunk
  -> 计算 chunk hash
  -> 上传或发送
```

下载时：

```text
创建 .flowplan_download 临时文件
按 chunk 写入指定位置
记录 chunk 状态
完成后校验整体 hash
校验通过后移动到最终路径
```

Android 端要考虑：

- 作用域存储。
- App 后台被系统杀死。
- 大文件写入权限。
- 下载目录选择。
- 充电和 WiFi 条件。
- 前台服务或通知显示长任务。

首版可以先要求用户保持 App 前台，后续再做后台传输。

## 10. 局域网直连设计

### 10.1 基础思路

目标设备临时启动一个本地 HTTP 接收服务：

```text
Android 或 Windows 目标设备
  -> 启动本地接收端口
  -> 向服务端上报 local_ip + port + token
  -> 源设备拿到候选地址
  -> 源设备尝试 HTTP PUT chunk
```

### 10.2 安全要求

每次传输必须有一次性 token。

```text
PUT http://local-ip:port/flowplan-transfer/session-id/chunk-index
Authorization: TransferToken ...
```

局域网内其他设备即使扫到端口，也不能上传或下载文件。

### 10.3 可达性探测

```text
源设备请求 /ping
目标设备返回 session_id 和 device_id
源设备确认匹配
开始传输
```

如果超时：

```text
候选标记 failed
尝试下一个策略
```

## 11. 同 WiFi 辅助发现

校园网环境中，广播发现常常不可靠。

FlowPlan Server 可以作为 rendezvous：

```text
设备 A 上报：SSID hash、本地 IP、端口、能力
设备 B 上报：SSID hash、本地 IP、端口、能力
服务端发现两者可能同 WiFi
  -> 给双方下发候选地址
  -> 双方互相探测
  -> 成功则直连
  -> 失败则进入 P2P 或服务端中转
```

注意：

- SSID hash 不是安全凭据。
- 不要长期保存 SSID 原文。
- 候选地址必须短期过期。
- 用户可以关闭“同 WiFi 辅助发现”。

## 12. P2P 设计

### 12.1 长期方案

使用 WebRTC DataChannel。

```text
FlowPlan Server 负责 signaling
coturn/STUN 负责 NAT traversal 辅助
客户端通过 DataChannel 传 chunk
```

### 12.2 首版不强依赖 P2P

P2P 复杂度较高，建议不作为 `[M]` 必备。

阶段划分：

```text
MVP：服务端中转 + 分块续传
V 阶段：局域网直连 + 同 WiFi 辅助发现
长期：WebRTC P2P + TURN 中继
```

### 12.3 P2P chunk 协议

DataChannel 消息类型：

```text
transfer_start
chunk_meta
chunk_data
chunk_ack
chunk_retry
transfer_complete
transfer_error
```

每个 chunk 必须 ack，失败可重传。

## 13. 断点续传规则

### 13.1 上传续传

```text
客户端查询 session
  -> 服务端返回已完成 chunk 列表
  -> 客户端跳过已完成 chunk
  -> 只上传 pending/failed chunk
  -> 全部完成后 complete
```

### 13.2 下载续传

```text
客户端读取本地临时文件和 chunk 状态
  -> 查询服务端对象信息
  -> 如果 hash/size 匹配，继续下载缺失 chunk
  -> 如果对象已变化，废弃旧临时文件或生成冲突提示
```

### 13.3 会话恢复

App 重启后：

```text
读取本地 transfer_sessions
  -> 找出 transferring/paused/failed 且可恢复的任务
  -> 显示在传输中心
  -> 用户选择继续或取消
```

## 14. 校验和完整性

### 14.1 分块校验

每个 chunk 上传/下载后计算 hash。

```text
chunk_index
byte_start
byte_end
chunk_sha256
```

服务端和客户端都要校验。

### 14.2 整体校验

传输完成后计算整体 SHA-256。

```text
expected_sha256 == actual_sha256
  -> completed
else
  -> checksum_failed
  -> 提示重新校验或重传失败部分
```

### 14.3 校验失败处理

不要静默使用损坏文件。

处理：

```text
标记会话 failed
保留临时文件
显示失败原因
允许重新下载失败 chunk
必要时删除临时文件重新开始
```

## 17. 同步、离线与冲突

### 17.1 哪些数据同步

| 数据 | 同步策略 |
|---|---|
| transfer_sessions | 同步摘要 |
| transfer_chunks | 可同步摘要，详细状态可只本地和服务端保存 |
| transfer_events | 同步关键事件 |
| device_network_presence | 服务端短期保存，不长期同步 |
| 文件内容 | 由传输协议处理，不走普通对象同步 |
| 完成后的 file_nodes | 必须同步或更新 |

### 17.2 离线场景

| 场景 | 处理 |
|---|---|
| 源设备离线 | 传输暂停 |
| 目标设备离线 | 等待目标上线或改为服务端中转 |
| 服务端离线 | 局域网直连可继续，否则暂停 |
| App 关闭 | 可恢复任务进入 paused 或 failed_recoverable |
| 网络切换 | 重新探测路径，必要时降级 |

### 17.3 冲突场景

| 场景 | 处理 |
|---|---|
| 目标路径已有同名文件 | 不覆盖，生成冲突候选或另存 |
| 传输中文件被修改 | 校验失败，提示重新选择版本 |
| 下载目标文件被用户外部编辑 | 不覆盖，另存或冲突处理 |
| 两个设备同时上传同一 file_node 新版本 | 进入 J 模块版本冲突 |
| 服务端中转对象过期但客户端还想续传 | 会话 expired，需要重新创建 |

## 18. 异常与边界情况

必须考虑：

1. 网络中断。
2. 网络从 WiFi 切到移动网络。
3. 服务端重启。
4. 客户端进程退出。
5. Android 后台被杀。
6. 磁盘空间不足。
7. 权限不足。
8. 文件被外部程序占用。
9. 文件传输中被修改。
10. 分块重复上传。
11. 分块乱序到达。
12. chunk hash 不一致。
13. 整体 hash 不一致。
14. 局域网候选不可达。
15. P2P 连接建立但中途断开。
16. 服务端临时文件清理失败。
17. 用户取消传输。
18. 会话过期。
19. 目标路径冲突。
20. 用户在多个端同时发起同一文件传输。

处理原则：

- 能恢复就恢复。
- 不能恢复就明确失败原因。
- 不静默覆盖目标文件。
- 不使用校验失败的文件。
- 不让失败任务无限重试。
- 不把临时文件永久堆积。

## 19. 安全与隐私

传输模块涉及文件内容，必须保守。

规则：

- 每次传输必须绑定用户、设备、会话和 token。
- 局域网直连也必须认证。
- 同 WiFi 辅助发现不能泄露 SSID 原文。
- 设备网络候选要短期过期。
- 服务端中转文件要有保留期限。
- 高敏感文件传输前可提示用户确认。
- 传输日志不要记录完整文件内容。
- 失败日志不要记录敏感路径全量内容，可做脱敏。
- 分享给其他用户或外部设备不属于首版范围。

## 20. 验收标准

### `[B] 骨架完成`

满足：

- 有 file_transfer_sessions。
- 有 file_transfer_chunks。
- 有创建上传/下载会话接口。
- 有 chunk 上传接口。
- 有 chunk 或 Range 下载接口。
- 有基础传输状态。

### `[M] MVP 可用`

必须实测：

- 用户能选择一个 10MB 文件上传到服务端。
- 用户能选择一个 500MB 文件分块上传到服务端。
- 上传中断后可以继续。
- 用户能从服务端下载文件。
- 下载中断后可以继续。
- 完成后整体 hash 一致。
- 客户端有传输进度 UI。
- 失败原因对用户可见。

### `[V] 已验证可用`

必须实测：

- 服务端重启后可恢复未完成上传。
- 客户端重启后可恢复未完成下载。
- 局域网直连可用。
- 同 WiFi 辅助发现可用。
- 直连失败后能自动降级服务端中转。
- 大文件不会导致内存暴涨。
- 目标路径冲突不会覆盖文件。

### `[S] 稳定可用`

必须具备：

- 传输状态机测试。
- chunk 重试测试。
- hash 校验测试。
- 网络中断测试。
- 服务端清理任务。
- 管理端传输诊断。
- Android 后台限制处理。
- 多周真实使用没有严重损坏或丢文件。
