# 第八部分：L 报告、日记、推送与现实上下文

## 1. 目标

L 模块的目标是把 FlowPlan 中的计划、实际记录、活动理解、任务推进、文件上下文和天气等信息，整理成用户能读、能修改、能确认、能推送的报告和日记。

本阶段重点不是做一个全自动“替用户下结论”的系统，而是做一个可靠的反馈闭环：

```text
计划数据
  + 实际记录
  + 活动片段
  + 任务实际投入
  + 文件上下文
  + 天气上下文
  -> 模板化生成报告/日记草稿
  -> 可选 LLM 润色或生成自然语言
  -> 用户编辑和确认
  -> 保存、同步、推送
  -> 后续排程和复盘可读取
```

本阶段范围：

1. 报告和日记必须支持模板生成。
2. LLM 生成是可选增强，不是唯一生成方式。
3. 没有 LLM 或 LLM 失败时，模板仍然能生成可用报告。
4. 天气保留 API 接入，用作出行、计划解释和日报上下文。
5. 位置暂不实现，仅保留未来接口和数据位。
6. 蓝牙暂不实现，仅作为未来探索方向。
7. 报告中的“事实、推断、AI 总结”必须区分。
8. 推送失败必须可追踪和重试。

一句话目标：

```text
先用模板稳定生成报告和日记，再用 LLM 提升表达质量；天气作为软上下文，位置和蓝牙后置。
```

## 3. 用户流程

### 3.1 生成日报：模板模式

```text
用户打开报告中心
  -> 选择“生成今日日报”
  -> 系统读取今天日程、任务、实际记录、活动片段、任务投入、文件上下文、天气
  -> 按日报模板生成报告草稿
  -> 用户查看事实、推断和待确认项
  -> 用户编辑
  -> 用户确认保存
```

模板模式生成的报告应该长这样：

```text
# 2026-04-27 日报

## 今日计划
- 高等数学课 09:50-10:35
- 数据库课程作业，预计 90 分钟

## 实际完成
- 10:50-12:15 完成数据库课程作业，来源：活动片段 + 用户确认
- 15:00-15:40 整理课程资料，来源：文件打开记录 + 活动推断

## 计划偏离
- 原计划 19:00-20:30 写作业，实际未执行。来源：计划片段 + 活动记录

## 明日风险
- 英语阅读未完成，剩余约 30 分钟

## 天气上下文
- 明日有降雨概率，出行任务建议预留缓冲
```

### 3.2 生成日报：LLM 润色模式

```text
用户点击“用 AI 润色”
  -> 系统只发送脱敏后的报告事实摘要给 LLM
  -> LLM 生成更自然的文字
  -> 系统保留原始模板结构和证据链接
  -> 用户确认后保存
```

LLM 不能改写事实，只能润色表达或生成总结。

### 3.3 生成自动日记草稿

```text
用户打开“自动日记”
  -> 系统读取当天已确认实际记录和活动摘要
  -> 使用日记模板生成草稿
  -> 用户可选择是否让 LLM 改写成更自然的日记
  -> 用户编辑
  -> 用户保存
```

日记草稿示例：

```text
今天上午主要完成了数据库课程作业，中间查阅了课件和 SQL 文档。晚上原计划继续推进英语阅读，但实际没有完成，需要明天补上。
```

注意：日记是用户私人表达，不能自动推送，除非用户明确开启。

### 3.4 推送报告

```text
用户开启日报推送
  -> 每天固定时间生成报告摘要
  -> 如果用户设置需要确认，则先进入待确认
  -> 确认后推送到 Telegram / Email / Webhook / 系统通知
  -> 推送成功或失败都写入 push_deliveries
```

推送失败：

```text
Telegram token 错误
  -> 标记 failed
  -> 显示失败原因
  -> 用户修改配置后点击重试
```

### 3.5 天气上下文

```text
用户在设置中配置常用地点，例如学校、宿舍、家
  -> 服务端低频调用天气 API
  -> 缓存当前天气和未来预报
  -> 报告生成时读取天气摘要
  -> 排程解释可使用天气作为软约束
```

示例：

```text
明天 08:00-10:00 有较高降雨概率，建议通勤或户外任务预留 15 分钟缓冲。
```

天气不能直接静默修改计划，只能作为建议和解释。

### 3.6 位置和蓝牙未来流程

当前不实现，只保留未来设想：

```text
未来位置：用户授权后采集地点摘要，用于判断上课、通勤、宿舍、图书馆。
未来蓝牙：判断手机和电脑/硬件是否在一起，用于设备是否随身等弱上下文。
```

当前报告不能依赖位置和蓝牙数据。

## 5. 模板系统

报告和日记必须先支持模板系统。

### 5.1 模板原则

```text
模板生成是基础能力
LLM 是可选增强
模板输出必须可读
模板输出必须保留证据来源
模板失败不能影响原始数据
```

### 5.2 模板结构

模板可以分为：

```text
daily_report
weekly_report
monthly_report
diary_entry
project_report
course_report
push_summary
```

### 5.3 模板变量

示例变量：

```text
{{date}}
{{planned_events}}
{{completed_tasks}}
{{actual_logs}}
{{task_work_summary}}
{{activity_segments}}
{{plan_deviations}}
{{top_apps}}
{{recent_files}}
{{weather_summary}}
{{sync_warnings}}
{{tomorrow_risks}}
```

### 5.4 模板输出中的证据标记

每条重要结论都应该能链接到来源：

```text
结论：今天主要完成了数据库课程作业。
来源：actual_activity_log:xxx、task_work_log:yyy、activity_segment:zzz
类型：已确认事实
```

报告中必须区分：

| 类型 | 说明 |
|---|---|
| fact | 已确认事实 |
| inferred | 系统推断 |
| ai_summary | AI 总结 |
| user_note | 用户备注 |
| external | 外部数据，例如天气 |

## 6. LLM 可选生成策略

### 6.1 LLM 可以做什么

LLM 可以：

```text
润色日报语言
生成自然语言日记草稿
总结一周趋势
解释计划偏离
把结构化数据变成更好读的文字
生成推送摘要
```

### 6.2 LLM 不能做什么

LLM 不能：

```text
把候选实际记录直接变成事实
擅自修改任务和日程
擅自删除报告证据
擅自读取完整敏感文件
擅自推送私人日记
把推断写成确定事实
```

### 6.3 LLM 输入

只发送脱敏摘要：

```text
已确认实际记录摘要
任务推进摘要
活动片段摘要
计划偏离摘要
天气摘要
用户备注
```

默认不发送：

```text
完整键盘输入
完整聊天内容
完整文件正文
精确位置轨迹
敏感窗口标题
```

### 6.4 LLM 输出约束

LLM 输出应包含：

```json
{
  "summary": "...",
  "sections": [],
  "uncertainClaims": [],
  "suggestedEdits": [],
  "sensitiveWarnings": []
}
```

FlowPlan 应检查：

- 是否把推断说成事实。
- 是否加入不存在的活动。
- 是否包含敏感内容。
- 是否违反模板结构。

### 6.5 无 LLM fallback

如果 LLM 不可用：

```text
使用模板生成报告
保留所有结构和证据
提示：AI 润色暂不可用
```

## 7. 天气 API 设计

### 7.1 天气的定位

天气是软上下文。

用途：

```text
日报解释
出行任务提醒
排程缓冲建议
户外任务风险
通勤提醒
```

天气不能：

```text
静默修改计划
静默移动任务
替代用户确认
```

### 7.2 天气 Provider

建议支持多 Provider：

```text
open_meteo
openweather
weatherapi
custom
```

推荐默认优先考虑 Open-Meteo：

- 不需要 API Key，适合个人项目和开发期。
- 可以按经纬度获取天气预报。
- 后续如果需要更复杂服务，可切换 OpenWeather 或 WeatherAPI。

OpenWeather 和 WeatherAPI 可作为备用或高级 Provider。

### 7.3 地点配置

由于位置暂不实现，天气地点由用户手动配置。

```text
学校：纬度、经度、时区
宿舍：纬度、经度、时区
家：纬度、经度、时区
默认地点：学校
```

可以后续支持：

```text
城市名搜索
地图选择
从日程地点推断
位置权限自动判断
```

但本阶段不依赖 GPS。

### 7.4 缓存策略

服务端低频缓存：

```text
当前天气：每 30-60 分钟更新
小时预报：每 1-3 小时更新
每日预报：每 6-12 小时更新
历史天气摘要：按需保存
```

避免客户端频繁直接打天气 API。

## 10. 报告生成流程

### 10.1 生成输入快照

```text
ReportGenerationService
  -> 查询日程
  -> 查询任务
  -> 查询排程片段
  -> 查询实际记录
  -> 查询活动片段
  -> 查询任务实际投入
  -> 查询文件上下文
  -> 查询天气摘要
  -> 生成 source_snapshot_json
```

### 10.2 模板渲染

```text
ReportTemplateService
  -> 加载默认模板
  -> 填充变量
  -> 生成 markdown
  -> 同时生成 report_entries 和 evidence_links
```

### 10.3 可选 LLM 生成

```text
如果用户开启 LLM：
  -> 对 source_snapshot 脱敏
  -> 调用 K 模块 AI Provider
  -> 返回润色后的报告草稿
  -> 保留模板结构和证据链接
```

### 10.4 用户确认

```text
用户编辑报告
  -> 保存 draft
  -> 用户确认
  -> status = confirmed
  -> 允许推送
```

## 13. 天气实现策略

### 13.1 Provider 抽象

```text
WeatherProvider
  getCurrent(location)
  getHourlyForecast(location, range)
  getDailyForecast(location, range)
  normalize(rawPayload)
```

### 13.2 Open-Meteo Provider

适合默认开发和个人使用。

输入：

```text
latitude
longitude
timezone
hourly variables
daily variables
```

输出统一成：

```text
temperature
precipitation_probability
weather_code
wind_speed
humidity
summary
```

### 13.3 OpenWeather / WeatherAPI Provider

作为可选 Provider：

- 用户自行填写 API Key。
- 服务端加密保存。
- Provider 失败时 fallback 到缓存。

### 13.4 天气进入报告

报告中天气只作为外部上下文：

```text
今日天气：多云，下午有降雨概率。
影响：外出任务建议预留缓冲。
```

不能写成确定因果：

```text
你因为下雨所以没有完成任务。
```

除非有用户备注或实际记录证据支持。

## 15. 同步、离线与冲突

### 15.1 哪些数据同步

| 数据 | 同步策略 |
|---|---|
| reports | 必须同步 |
| report_entries | 必须同步 |
| report_evidence_links | 必须同步 |
| diary_entries | 必须同步，但可设置仅本地私密 |
| report_templates | 同步 |
| push_channels | 同步配置摘要，敏感字段加密 |
| push_deliveries | 同步 |
| weather_locations | 同步 |
| weather_cache | 可服务端缓存，客户端按需拉取 |
| reality_context_sources | 同步占位配置 |
| 原始位置/蓝牙数据 | 本阶段不存在 |

### 15.2 离线规则

| 场景 | 处理 |
|---|---|
| 离线生成报告 | 可以基于本地数据和缓存天气生成 |
| 离线 LLM 润色 | 云端 LLM 不可用，本地模型可选 |
| 离线推送 | 进入待推送队列 |
| 离线刷新天气 | 使用缓存并标注可能过期 |
| 离线编辑日记 | 本地保存，联网后同步 |

### 15.3 冲突场景

| 场景 | 处理 |
|---|---|
| 两端同时编辑同一报告 | 生成冲突或保留双草稿 |
| 一端确认报告，另一端继续编辑草稿 | 提示报告已确认，编辑另存为新版本 |
| 日记多端编辑冲突 | 保留双版本，人工合并 |
| 推送配置冲突 | 最近确认配置优先，并写审计 |
| 天气缓存冲突 | 以服务端最新缓存为准 |

## 16. 异常与边界情况

必须考虑：

1. 报告生成时没有实际记录。
2. 活动片段全是低置信度。
3. 任务数据缺失。
4. 天气 API 失败。
5. 天气缓存过期。
6. LLM API 失败。
7. LLM 编造不存在的事实。
8. Telegram token 错误。
9. Email SMTP 配置错误。
10. Webhook 返回失败。
11. 推送重复发送。
12. 用户编辑报告时另一端确认。
13. 日记包含敏感内容。
14. 报告过长导致推送渠道限制。
15. 模板变量缺失。
16. 模板语法错误。

处理原则：

- 模板生成必须能 fallback。
- LLM 失败不能导致报告不可生成。
- 推送失败必须可重试。
- 报告必须标注数据不足。
- AI 生成内容必须保留可编辑状态。
- 日记默认私密。

## 17. 安全与隐私

报告和日记可能汇总大量隐私信息。

规则：

- 日记默认不推送。
- 报告推送默认只推摘要，不推完整敏感内容。
- LLM 输入使用脱敏摘要。
- 用户可关闭某些数据源进入报告。
- 用户可关闭天气。
- 位置和蓝牙本阶段不采集。
- 报告证据链中敏感窗口标题可脱敏展示。
- 推送渠道配置中的 token 加密保存。
- Webhook 推送要提示可能发送到第三方服务。
- 删除报告和日记需要确认。

## 18. 验收标准

### `[B] 骨架完成`

满足：

- 有 reports / diary_entries 或等价表。
- 有报告生成服务。
- 有报告页面。
- 有推送队列。
- 有 Telegram/Email/Webhook/System Notification 中至少一个出站基础。
- 有天气 Provider 的接口设计或基础实现。

### `[M] MVP 可用`

必须实测：

- 用真实一天数据生成日报模板草稿。
- 日报中能区分事实、推断、AI 总结。
- 用户能编辑并确认日报。
- 用户能生成自动日记草稿。
- 用户能编辑并保存日记。
- 没有 LLM 时模板仍可用。
- 有 LLM 时可以选择润色。
- 天气 API 能获取默认地点天气并进入报告。
- Telegram 或系统通知至少一种推送成功。
- 推送失败有记录和重试。

### `[V] 已验证可用`

必须实测：

- 连续多天生成日报。
- 周报能引用多天日报和任务趋势。
- 日报证据链可点击查看来源。
- LLM 不会把推断写成确定事实，或系统能标出风险。
- 天气 API 失败时使用缓存或提示不可用。
- 日记多端同步不丢失。
- 推送重复发送有防护。

### `[S] 稳定可用`

必须具备：

- 模板渲染测试。
- 报告证据链测试。
- LLM fallback 测试。
- 推送失败重试测试。
- 天气 Provider 失败测试。
- 隐私脱敏测试。
- 多周真实使用后报告质量可接受。
