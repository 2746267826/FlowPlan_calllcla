# FlowPlan 完成度复核与模型后续计划（2026-04-29）

本文用于固定当前架构判断、功能完成度和后续模型开发路线，避免后续上下文丢失。当前最高只按代码级 MVP 记录，不把未真实验收的能力标为 `[V]` 或 `[S]`。

## 1. 当前总体判断

FlowPlan 已经进入“服务端事实库 + 管理端 + 多端客户端”的代码级 MVP 阶段：

- 服务端：承担事实库、同步、文件、排程、活动理解、报告、AI 草案和审计。
- 管理端：承担全局数据、设置、设备、同步、日志、文件、模型和运维可见性。
- Flutter Windows/Android：作为日常入口，可保留本地缓存、离线队列和原生追踪能力。
- Flutter Web：作为浏览器版客户端，只访问服务端事实库，不做本地追踪和本地 SQLite 事实缓存。

当前最大风险不是“没有表或接口”，而是多个模块仍缺真实规模、真实设备、真实数据的端到端验证。因此当前大多数模块只能是 `[M]` 或 `[M-]`，不能标为 `[V]`。

## 3. 模型完善度

### 3.1 模型运行底座

已存在的模型定义：

- `scheduler.v1`
- `activity_merge.v1`
- `report_template.v1`
- `file_recommendation.v1`
- `deviation_detection.v1`

已有能力：

- 模型定义、版本、运行记录、反馈事件、规则配置。
- LLM 健康状态、LLM 草案托底、受控 AI 草案审计。
- 简单反馈学习和规则版本激活。

不足：

- 学习仍是浅层规则权重调整，不是训练或微调。
- 缺稳定回归样本集和模型评估流程。
- 文件推荐、偏离检测还没有达到可依赖智能程度。
- 低风险自动启用规则的判断仍需更严谨。

状态：`[M-]`。

### 3.2 排程模型

当前服务端排程能力：

- 读取任务、阻挡日程、实际投入。
- 根据实际投入扣减任务剩余时间。
- 生成排程草案，不直接写库。
- 用户确认后写入 `task_schedule_segment`，并生成 `sync_changes` 和 `audit_logs`。
- 低置信度或未排任务过多时可调用 LLM 托底。
- LLM 只能生成草案，服务端会验证范围、阻挡块和任务约束。

本次已推进：

- 支持 `locked` 任务不参与自动排程。
- 支持 `allowAutoSchedule=false` 任务不参与自动排程。
- 支持任务可排时间窗：`earliestStart / availableAfter / notBefore / startAfter` 与 `latestEnd / availableBefore / notAfter / endBefore`。
- 支持任务拆分限制：`canSplit / splittable`、`minChunkMinutes`、`maxChunkMinutes`。
- 支持地点和备注进入排程解释：`location / place / where`、`notes / description / remark`。
- 支持从远程设置读取工作时间：`scheduler.policy`、`work.time`、`working_hours`、`work_hours`、`user.preference`。
- 支持基础周期阻挡日程展开：daily / weekly / monthly，以及 weekday 过滤。
- LLM 草案校验增加任务锁定、自动排程开关、任务时间窗、块长度限制。

仍然不足：

- 算法仍是贪心排序 + 空闲块填充，不是全局优化。
- 工作时间设置 schema 需要继续规范。
- 周期日程只做基础展开，不是完整 RFC RRULE。
- 地点、天气、文件上下文目前主要进入解释，还没有深度影响评分。
- 用户历史偏好学习仍浅。

状态：`[M-]`，但比之前更接近真实可用排程。

### 3.3 活动理解模型

当前能力：

- 读取服务端追踪数据。
- 按时间间隔、应用、窗口、文件路径合并 `activity_segments`。
- 生成标题、时间范围、主要应用、窗口、证据和置信度。
- 根据任务标题、窗口标题、文件路径尝试关联任务。
- 用户确认后生成 `actual_activity_logs` 和 `task_work_logs`。
- 用户确认、拒绝、修正进入模型反馈。

不足：

- 合并规则仍粗，复杂场景容易误分或误合并。
- 应用分类、通信打断、文件路径权重仍需真实数据校准。
- LLM 只适合作解释建议，不能直接确认事实。
- 原生客户端追踪上传质量还需要验证。

状态：`[M-]`。

### 3.4 报告、AI 与文件模型

- 报告模型：模板优先、LLM 可选润色，有 evidence links，但还需真实日报数据验证。
- AI 工具模型：目前只应把 `create_task` 作为可执行 MVP；其他高风险操作必须继续草案化或禁用。
- 文件推荐模型：已有服务端模型定义和部分文件上下文，但仍需结合任务、日程、历史打开记录和云盘副本状态继续完善。
- 偏离检测模型：已有基础检测，但需要和重排草案、报告证据和用户反馈串起来。

## 4. 后续开发计划

### P0：真实验收与状态校准

目标：确认代码级 MVP 是否真的可用。

- 两个客户端验证任务/日程同步。
- 断网创建任务，恢复网络后自动同步。
- 双端修改同一任务，确认生成冲突而不是静默覆盖。
- 上传一天真实追踪数据。
- 活动片段确认后生成实际记录和任务投入。
- 实际投入影响排程剩余时间。
- 服务端排程草案确认后写入排程片段。
- Web 端看到与 Windows 端一致的任务、日程、文件、报告。
- 管理端看到设备、同步、日志、模型运行、AI 草案、报告推送。

### P1：排程模型继续升级

目标：从“能排”升级到“更符合真实生活”。

- 规范远程工作时间设置 schema。
- 完整支持周期课表和阻挡任务。
- 地点、天气、文件上下文进入评分，而不仅是解释。
- 支持任务可排日期、固定偏好时段、上下文切换成本。
- 未排原因更细化：时间不足、阻挡冲突、时间窗不匹配、禁止自动排程、不可拆分。
- 用户拒绝、修改、手动重排沉淀为评估样本。
- 建立历史日期回放测试。

### P2：活动理解模型优化

- 原生追踪缓冲分批、压缩、断点上传。
- 服务端 raw 数据去重、异常隔离、质量评分。
- 应用分类规则库。
- 文件路径和任务绑定增强。
- 低置信度片段集中审核。
- 反馈学习调整合并阈值和任务匹配权重。

### P3：模型中心与学习能力

- 模型运行次数、失败率、平均置信度、用户接受率。
- 输入摘要、输出摘要、规则版本和失败原因可查。
- 反馈自动沉淀为 `model_eval_cases`。
- 学习生成新规则版本前必须跑评估。
- 大幅规则变化必须管理端确认。
- 支持规则版本回滚。
- LLM 只能建议规则变更，不能自动启用。

### P4：云盘与文件模型完善

- `file_nodes` 作为唯一逻辑文件树。
- 客户端只拉文件树和元数据，访问时才传输内容。
- 云盘目录与本地目录绑定。
- 下载前检查本地同路径或同 hash 文件。
- hash 相同直接登记本地副本并打开。
- hash 不同提示冲突，不覆盖。
- 文件推荐由服务端根据任务、日程、最近使用、历史打开记录生成。

### P5：报告、日记、推送增强

- 报告展示明确证据来源。
- 用户编辑日报后的差异进入模型反馈。
- 日记模板学习用户写作偏好。
- 天气、实际投入、排程偏离、文件活动共同进入日报。
- Telegram/Webhook 推送失败可重试。

### P6：高级外部能力

这些仍是未来能力，不应虚假标为完成：

- OneDrive OAuth/Graph 双向同步。
- LAN/P2P/TURN 多路径传输。
- Android 真机长期追踪。
- 位置记录和蓝牙长连接记录。
- Telegram 入站自然语言控制。
- Outlook 写入自动化。
- 完整 OpenClaw 式工具生态。
- 长期个性化模型学习。
