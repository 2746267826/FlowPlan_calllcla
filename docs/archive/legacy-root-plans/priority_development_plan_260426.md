# FlowPlan P0-P12 优先级开发总计划（2026-04-26）

> 已整理归档：新的权威计划入口为 `docs/planning/master_priority_plan_260426.md`。本文保留为 2026-04-26 阶段性来源文件。

## 0. 文档定位

本文把当前所有开发想法重新整理为从基础到细节的优先级路线图。它的重点是“先做什么、后做什么、每一阶段为什么必须在这个位置”，用于后续拆分任务、排期和验收。

本计划不写具体代码实现，只定义产品目标、数据边界、模块边界、阶段任务和验收标准。

## 1. 总体目标

FlowPlan 的长期目标是一个以时间为主轴的个人执行系统：

```text
日程 / 任务 / 追踪 / 实际记录 / 文件 / AI / 服务端 / Web / 聊天推送
```

它最终应做到：

- 计划知道“应该做什么”。
- 追踪知道“实际做了什么”。
- 文件系统知道“做这件事需要哪些材料”。
- 服务端保存完整数据并提供跨端同步、统计聚合和 Web 管理。
- AI 能理解上下文，但只能生成预案，不能绕过人工确认。
- 日报、周报、月报和自动日记能定期生成，并可推送到 Telegram 等聊天渠道。

## 2. 不变原则

1. 服务端完整存储  
   所有信息最终都应同步到服务端。客户端保留本地缓存和离线写入能力。

2. 本地可用  
   网络差时，本机仍能查看、创建、修改数据，并标识“未与云端同步”。

3. 服务端统计聚合  
   热力图、趋势图、输入统计、区间分析、日报统计等大量数据计算由服务端查表聚合，客户端只拿最终结果和少量明细。

4. 自动操作必须确认  
   自动排程、AI 修改、同步冲突处理、文件移动、批量操作等都先生成预案，再由用户确认。

5. 全部可追溯  
   关键操作写审计日志。高频追踪原始写入不进入普通审计，但其管理、清理、同步、导入导出必须审计。

6. 隐私分层  
   原始键盘、聊天、位置等敏感数据即使进入自有服务端，也不得直接进入第三方 LLM API。外部 AI 只接收脱敏摘要。

7. 模块独立，信息综合  
   功能模块独立开发，但统一汇入 `UserContext`，供排程、日报、AI 和文件推荐使用。

8. 保留 Flutter 主客户端  
   Windows/Android 主客户端继续使用 Flutter。P0-P3 的目标是把 Flutter 从“本地单体大脑”重构为“跨平台客户端外壳 + 本地缓存 + 原生采集 + 人工确认界面”，而不是重写客户端。

9. Web 管理面板独立建设  
   服务端管理面板优先使用 Web 技术栈（Next.js 或 Vite React）。Flutter Web 可以作为未来轻量入口，但不作为复杂管理后台的主路线。

## 3. 总体优先级概览

```text
P0  架构定调与服务端/客户端分离底座
P1  数据同步、本地缓存、同步状态与冲突模型
P2  服务端统计聚合与追踪查询性能
P3  客户端重构与大页面拆分
P4  实际记录系统与阻挡日程自动候选
P5  追踪融合模型：活动片段、活动理解、任务实际投入
P6  排程模型升级：读取真实状态并生成可解释预案
P7  日报、周报、自动日记与聊天推送
P8  文件管理与文件上下文
P9  云文件、OneDrive 与服务端存储共存
P10 AI 聊天与受控工具调用
P11 位置、天气、蓝牙与外部上下文
P12 Web 管理面板、长期智能与生态入口
```

## P1：数据同步、本地缓存、同步状态与冲突模型

### 目标

让所有核心信息最终同步到服务端，同时本机保留可用副本。网络差时可继续使用，并清楚显示未同步状态。

### 必须同步的数据

第一批：

- 用户、设备。
- 日历本、任务本。
- 日程、任务。
- 排程片段。
- 实际记录。
- 操作审计。
- 跨端必要设置。

第二批：

- 活动片段。
- 活动理解结果。
- 任务实际投入记录。
- 文件元数据。
- 文件绑定关系。
- AI 对话摘要与操作预案。

第三批：

- 原始活动日志。
- 键鼠输入事件。
- 位置采样。
- 更完整的 AI 会话。

第三批可后台分批、压缩、延迟上传，不要求实时阻塞。

### 客户端同步状态

所有可变数据应有同步元信息：

```text
sync_state:
  synced
  pending_create
  pending_update
  pending_delete
  conflict
  failed

local_version
server_version
last_synced_at
last_sync_error
origin_device_id
```

### UI 要求

- 未上传显示“未同步”。
- 正在等待服务端确认显示“等待同步”。
- 同步失败显示原因和重试入口。
- 冲突显示“需要处理”。
- 离线修改不假装已同步。

### 冲突策略

- 不静默覆盖。
- 字段级冲突尽量展示字段差异。
- 用户可选本地、服务端或手动合并。
- 冲突处理写审计。

### 验收

- 断网时能创建任务/日程。
- 恢复网络后可同步。
- 同一字段多端修改不会被静默覆盖。

## P3：客户端重构与大页面拆分

### 目标

降低继续开发的复杂度，避免巨型页面继续膨胀。

P3 不是全量重写 Flutter，也不是迁移到 Electron/Tauri/React Native。P3 的重点是把现有 Flutter 客户端拆成更清晰的端侧模块，让它成为服务端架构下的稳定客户端：

- UI 层只负责展示、输入、确认和本地交互。
- Repository 层通过本地 Drift 缓存和同步适配器读取数据。
- 高成本统计默认调用服务端聚合 API。
- Windows/Android 原生能力继续通过平台插件或轻量 sidecar 补强。
- 所有自动操作在 Flutter 客户端形成可确认预案。

## P4：实际记录系统与阻挡日程自动候选

### 目标

明确区分“计划”和“实际”。日程/任务是计划，追踪是证据，实际记录是最终事实。

### 新增实际记录模型

```text
actual_activity_logs
  title
  start_at
  end_at
  source_type
  source_id
  confidence
  confirmed_by_user
  evidence_json
```

### 阻挡日程候选

对于 `isBlock = true` 的日程：

- 时间已结束。
- 状态不是取消。
- 对应时间段没有其他已确认实际记录。
- 没有强冲突追踪证据。

则生成实际记录候选。

### 用户确认

- 确认。
- 改名确认。
- 忽略。
- 合并到已有实际记录。

### 验收

- 课表、会议、考试能自动生成实际记录候选。
- 用户确认后才成为正式实际记录。
- 结果进入日报、周报和排程反馈。

## P5：追踪融合模型

### 目标

把碎片追踪记录变成可用于任务判断和排程的结构化信息。

### 数据流

```text
原始活动 / 输入事件 / 日志
-> 活动片段 activity_segments
-> 活动理解 activity_interpretations
-> 任务实际投入 task_work_logs
-> 用户上下文 UserContext
```

### 活动片段

需要包含：

- 起止时间。
- 主要应用。
- 主要分类。
- 窗口关键词。
- 输入摘要。
- 中断次数。
- 专注分。
- 证据引用。

### 活动理解

输出：

- 活动类型。
- 关联任务。
- 置信度。
- 有效工作分钟。
- 进度信号。
- 自然语言摘要。

### LLM 使用

只在低置信度、多候选接近、用户主动分析、日报生成等场景使用。

### 验收

- 一天追踪能整理成 5-20 个活动片段。
- 高置信度片段能关联任务。
- 任务详情能看到实际投入证据。

## P6：排程模型升级

### 目标

让排程读取真实状态，而不是只根据任务列表机械安排。

### 排程输入

- 固定日程。
- 阻挡日程。
- 未排任务。
- 已排但可移动任务。
- 任务实际投入。
- 任务剩余时间。
- 用户疲劳状态。
- 用户习惯时间段。
- 文件上下文。
- 地点/天气等外部上下文。

### 排程输出

- 排程预案。
- 每个任务的安排原因。
- 未排原因。
- 冲突说明。
- 需要用户确认的变更。

### 原则

```text
生成预案 -> 用户确认 -> 写入排程片段 -> 写审计
```

### 验收

- 实际投入会影响剩余时间。
- 偏离计划后可生成重排预案。
- 自动操作不静默写库。

## P7：日报、周报、自动日记与聊天推送

### 目标

综合日程、任务、追踪、实际记录、文件、位置、天气等信息，定期生成日报、周报、月报和自动日记。报告不仅在软件中显示，也能推送到 Telegram 等聊天渠道。

### 报告类型

1. 日报  
   每天总结计划执行、实际活动、任务推进、偏离、文件使用、明日风险。

2. 周报  
   总结一周任务完成、时间分布、拖延模式、高效时段、项目进度。

3. 月报  
   总结长期趋势、任务类型占比、作息变化、文件/项目活跃度。

4. 自动日记  
   以自然语言记录“今天发生了什么”，可偏生活化，不只是统计表。

5. 专项报告  
   例如某个任务、项目、课程、文件夹、时间段的复盘。

### 日报输入

- 当天日程。
- 阻挡日程实际候选。
- 任务排程片段。
- 任务完成情况。
- 实际记录。
- 活动片段和活动理解。
- 输入统计。
- 应用使用排行。
- 文件打开/修改记录。
- 位置/天气上下文。
- 同步状态和冲突状态。

### 日报输出

结构化字段：

```text
report_date
planned_blocks
actual_blocks
task_progress
focus_summary
deviation_summary
top_apps
file_context
risks_for_tomorrow
suggested_actions
natural_diary
```

自然语言内容：

- 今日概览。
- 做成了什么。
- 哪些计划偏离了。
- 哪些任务需要明天继续。
- 有哪些自动候选记录等待确认。
- 一段可保存为日记的文字。

### 推送渠道

第一阶段：

- 软件内日报页。
- 系统通知提醒“日报已生成”。

第二阶段：

- Telegram Bot 推送日报摘要。
- Telegram 中点击链接打开详情。
- 可在 Telegram 回复简单操作，例如“确认实际记录候选 1”“明天提醒我继续”。

第三阶段：

- 邮件推送。
- Webhook。
- 其他聊天渠道。

### Telegram 要求

- 用户绑定 Telegram Chat ID。
- 支持开关：
  - 是否推送日报。
  - 是否推送周报。
  - 是否推送待确认事项。
  - 是否允许 Telegram 回复触发操作草稿。
- Telegram 里触发的写操作必须仍然走确认流程。

### 自动日记原则

- 自动生成，但不自动替用户确认事实。
- 不确定内容要表达为“可能”“看起来”。
- 用户可以编辑后保存。
- 保存后的日记进入服务端同步。

### 服务端职责

- 定时生成报告。
- 调用统计 API 获取聚合数据。
- 低频调用 LLM 生成自然语言。
- 保存报告版本。
- 推送 Telegram。

### 客户端职责

- 展示报告。
- 让用户确认/修改报告中的候选事实。
- 展示报告生成依据。

### 建议新增表

```text
periodic_reports
report_items
diary_entries
notification_channels
telegram_bindings
report_delivery_logs
```

### 验收

- 每天可生成日报。
- 日报能引用实际记录、任务推进和追踪摘要。
- 可在软件中查看。
- 可推送到 Telegram。
- 推送失败有日志和重试。
- 日记可编辑、保存、同步。

## P11：位置、天气、蓝牙与外部上下文

### 目标

让系统获得更多现实上下文，提高日报、实际记录和排程准确性。

### 位置

- 默认关闭。
- 低频采样。
- 支持地点别名。
- 可用于判断上课、通勤、外出。

### 天气

- 作为日报解释和排程软约束。
- 不直接硬性改日程。

### 蓝牙 / STM32

- 长期实验能力。
- 记录是否与手机连接。
- 用于防遗落和存在性判断。

### 验收

- 上下文进入报告和建议，但不静默写关键事实。

## P12：Web 管理面板、长期智能与生态入口

### Web 管理面板

技术路线：Web 管理面板独立建设，优先采用 Next.js 或 Vite React，不依赖 Flutter Web 作为主实现。Flutter 客户端仍然提供日常使用入口，Web 管理面板承担服务端管理、审计、统计和远程配置。

必须具备：

- 日程管理。
- 任务管理。
- 实际记录管理。
- 追踪摘要查看。
- 热力图和统计图。
- 文件元数据管理。
- 同步状态查看。
- 冲突处理。
- 审计日志查看。
- 报告管理。
- Telegram 推送配置。

### 长期智能

- 任务耗时预测。
- 高效时段学习。
- 文件推荐。
- 自动日报质量优化。
- 周/月趋势分析。
- 规则进化建议。

### 外部入口

- Telegram Bot。
- 分享入口。
- Webhook。
- 未来再考虑 QQ/微信等更复杂入口。

## 4. 最推荐的近期执行顺序

第一组：基础架构

1. P0：确定前后端分离架构。
2. P1：设计同步状态和离线队列。
3. P2：追踪查询性能和服务端统计 API 设计。

第二组：数据可信

4. P4：实际记录系统。
5. P5：追踪融合模型。
6. P6：排程读取真实状态。

第三组：输出与反馈

7. P7：日报、周报、自动日记、Telegram 推送。

第四组：扩展能力

8. P8：本地文件管理。
9. P9：云文件与 OneDrive。
10. P10：AI 聊天。
11. P11：位置天气蓝牙。
12. P12：Web 管理面板和长期智能。

## 5. 当前最不建议优先做

- 直接训练大模型。
- 端到端让 AI 读取全部原始日志并直接排程。
- 一开始就深度控制 QQ/微信。
- 一开始就做 STM32 硬件。
- 一开始就做完整 CP-SAT。
- 在客户端下载全部服务端追踪原始数据来画图。
- 当前阶段全量迁移到 Electron、Tauri 或 React Native。
- 用 Flutter Web 承担复杂服务端管理后台。
- 为了 Windows 文件管理和右键菜单能力整体替换现有 Flutter 客户端。

## 6. 一句话结论

FlowPlan 的正确路线应是：

```text
先服务端化和同步状态
再性能聚合和实际记录
再追踪融合和真实排程
再日报/日记/Telegram 输出
再文件、AI、位置天气和 Web 管理
```
