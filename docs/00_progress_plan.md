## 0. 状态标记规则

原来的 `[x]` 保留，但不再只表示“完成”。后续建议使用更细的状态。

| 标记 | 名称 | 含义 | 能否认为真实可用 |
|---|---|---|---|
| `[ ]` | 未开始 | 没有代码，或只有想法 | 否 |
| `[~]` | 设计中 | 已确定方向、数据结构、接口草案或技术路线 | 否 |
| `[B]` | 骨架完成 | 表、接口、Provider、页面入口、管理端基础存在 | 否 |
| `[M]` | MVP 可用 | 能走通一个真实用户流程，但异常和边界还不完整 | 部分可用 |
| `[V]` | 已验证可用 | 用真实数据或真实设备端到端验证过 | 基本可用 |
| `[S]` | 稳定可用 | 有异常处理、性能验证、日志、回归测试和长期使用验证 | 是 |

### 打标原则

- Codex 可以把 `[ ]` 推进到 `[B]`，但不能轻易宣称 `[V]` 或 `[S]`。
- 只有用户实际运行、操作、验证过的功能，才允许进入 `[M]` 或 `[V]`。
- 涉及同步、冲突、文件传输、AI 写操作、历史版本恢复、外部系统写入的功能，必须端到端验证后才能超过 `[M]`。
- 当前旧文档里的大量 `[x]` 应先理解为“代码骨架或接口基础已经做了”，不等同于“真正稳定可用”。

## 2. 阶段推进路线

### 阶段 0：整理与复核阶段

目标：不要继续盲目往后叠功能，先确认已经打钩的部分到底是 `[B]`、`[M]` 还是 `[V]`。

| 编号 | 任务 | 状态 | 验收方式 |
|---|---|---|---|
| R0.1 | 建立新版状态标记体系 | `[M]` | 本文档确认后即可使用 |
| R0.2 | 把旧 P0-P15 映射到新 A-L 功能域 | `[M]` | 本文档已经完成初版 |
| R0.3 | 逐模块复核代码真实状态 | `[ ]` | Codex 按模块列出已有文件、接口、页面和缺口 |
| R0.4 | 建立“不能随便打 V/S”的规则 | `[M]` | 后续所有文档统一使用 |
| R0.5 | 建立每次 Codex 输出模板 | `[ ]` | 每次必须说明修改文件、实现内容、剩余风险、手动验证步骤 |

优先级：最高。  
原因：如果不先复核，继续做 P12/P13 会让系统变成“每个模块都有一点，但都没真的闭环”。

### 手动验收要求

1. 执行 `server` 的 `npm run db:schema`，确保新增设备撤销字段入库。
2. 启动服务端后访问 `/api/health` 和 `/api/admin/monitoring/health`，确认数据库、存储、同步积压、模型计数能返回。
3. 注册两个设备，管理端查看在线状态；撤销其中一个设备，确认该设备 heartbeat 返回 `device_revoked/authRequired`。
4. 用两个客户端或模拟请求完成任务/日程断网写入、恢复 push、另一端 pull。
5. 制造同一对象版本冲突，用 `sync/conflicts/:id/resolve` 解决，确认 `audit_logs` 产生记录。
6. 用真实追踪数据生成 activity segments，确认一个 segment 后检查 `actual_activity_logs` 和 `task_work_logs`。
7. 用真实任务、阻挡日程、实际投入生成服务端排程草案，拒绝时不写库，确认时写入排程片段。
8. 文件中心添加真实 Root，确认文件夹和文件均可见；绑定任务；路径失效后 relink。
9. 使用文件传输上传/下载真实文件，查询 `/api/files/transfers/:sessionId/progress`，验证中断续传和 hash 校验。
10. 配置 Kopia 后创建快照、查看历史版本、下载副本，确认不会覆盖当前文件。
11. 配置 AI Provider，发送“帮我创建一个明天截止的数据库作业任务”，拒绝不写库，确认后任务真实出现且审计完整。
12. 生成日报/日记，编辑确认，配置推送渠道后验证推送成功或失败可重试。
