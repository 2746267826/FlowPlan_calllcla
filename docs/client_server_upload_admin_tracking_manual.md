# 客户端上传与管理端查数操作手册

本文用于验收和排查 Windows 客户端数据上传到服务端、Web 管理端查看服务端存储数据的流程。重点是追踪上传链路。

默认地址：

- 服务端 API：`http://localhost:3200/api`
- Web 管理端：`http://localhost:5173`

## 1. 启动与连接

1. 启动服务端前，确认 PostgreSQL 可用，并且服务端 schema 已执行过。
2. 启动服务端：

   ```powershell
   cd server
   npm run dev
   ```

3. 启动 Web 管理端：

   ```powershell
   cd web_admin
   npm run dev
   ```

4. 打开 Windows 客户端，进入“服务端同步”页。
5. 在“服务端 API 地址”中填写 `http://localhost:3200/api`。
6. 点击“启动检查并同步”。

连接状态说明：

- 绿灯或“服务端事实库模式”：客户端已完成 bootstrap/heartbeat，可以和服务端同步。
- “本地缓存模式”：客户端先显示本地数据，服务端连接尚未完成或刚启动。
- “等待同步”：本地有待上传的 mutation。
- “同步失败”：本地 mutation 上传失败，需要查看失败原因。
- “上次启动检查”：最近一次 bootstrap 时间。
- “上次同步”：最近一次 push/pull 同步时间。

客户端刚打开时短暂红字、随后绿灯，通常表示启动期先显示本地缓存或临时错误，后续 heartbeat/bootstrap 已恢复。若红字持续存在，再按本文“排错”处理。

## 2. 普通业务数据上传

任务、日程、实际记录、报告等业务数据主要通过两条路径进入服务端：

- server-first 写入：客户端在线时直接请求服务端，服务端写入事实库。
- 离线 mutation：客户端离线或请求失败时先写本地队列，恢复网络后上传服务端。

操作步骤：

1. 在 Windows 客户端创建或修改任务、日程、实际记录、报告等数据。
2. 打开“服务端同步”页。
3. 点击“立即同步全部”。
4. 等待“等待同步”数量下降，“同步失败”保持为 0。
5. 打开 Web 管理端查看服务端数据。

管理端查看入口：

- “数据中心”：任务、日程、实际记录、活动片段、追踪上传批次、排程运行。
- “同步与客户端”：客户端设备、服务端变更日志、客户端 mutation、同步冲突。
- “报告与推送”：报告、报告条目、证据链接、推送记录。

## 3. 追踪数据上传

追踪数据来自 Windows 客户端本地采集和整理，主要包含三类：

- `activity_record`：聚合后的活动记录。
- `tracked_input_event`：键盘/鼠标输入统计事件，不是原文输入内容。
- `raw_activity_log`：更原始的活动日志。

追踪上传流程：

1. 客户端读取本地尚未上传的追踪记录。
2. 客户端请求服务端创建 ingest batch。
3. 客户端按 chunk 上传记录。
4. 客户端请求 complete batch。
5. 服务端校验并接收记录。
6. 服务端将被接受的追踪记录写入 canonical `sync_objects`。
7. 管理端显示批次、接收数量、拒绝数量和错误原因。

涉及 API：

- `POST /api/tracking/ingest/batches`
- `POST /api/tracking/ingest/batches/:batchId/chunks`
- `POST /api/tracking/ingest/batches/:batchId/complete`
- `GET /api/tracking/summary`

用户操作步骤：

1. 在 Windows 客户端开启追踪，或先产生一段真实使用数据。
2. 保持服务端在线。
3. 打开“服务端同步”页，点击“启动检查并同步”或“立即同步全部”。
4. 打开 Web 管理端。
5. 进入“数据中心”。
6. 打开“追踪上传批次”。
7. 查看是否出现新的批次，状态为 `completed` 或 `completed_with_rejections`。

追踪上传批次重点字段：

- `batchUid`：客户端生成的批次标识。
- `dataKind`：本批次的数据类型，例如 `activity_record`、`tracked_input_event`、`raw_activity_log`。
- `status`：批次状态。
- `rawEventCount`：原始记录数。
- `acceptedEventCount`：服务端接受的记录数。
- `rejectedEventCount`：服务端拒绝的记录数。
- `errorMessage`：失败原因。
- `deviceName`：上传数据的客户端设备名。

批次状态解释：

- `open`：批次已创建，还没开始接收 chunk。
- `receiving`：服务端正在接收 chunk。
- `completed`：全部记录已处理且没有拒绝。
- `completed_with_rejections`：批次完成，但部分记录格式或内容不被服务端接受。
- `failed`：批次处理失败，需要查看 `errorMessage`。

## 4. 从追踪到可读事实

追踪上传成功不等于已经生成“实际记录”。数据会经过几层：

- 本地缓存数据：只在客户端本机，服务端还看不到。
- 已上传追踪数据：服务端已收到原始或聚合追踪记录，管理端可在“追踪上传批次”和服务端对象中看到。
- 活动片段：服务端活动理解将追踪数据合并为可读时间段，管理端在“活动片段”查看。
- 实际记录：用户确认活动片段后写入 `actual_activity_logs`，管理端在“实际记录”查看。
- 任务投入：若确认时关联任务，会写入 `task_work_logs`，管理端可在“任务投入”或相关数据集中查看。

推荐验收顺序：

1. 先看“追踪上传批次”，确认原始数据进入服务端。
2. 再看“活动片段”，确认服务端生成候选片段。
3. 确认一个活动片段。
4. 再看“实际记录”，确认用户确认后的事实写入服务端。
5. 如果关联了任务，再看任务投入和后续排程结果。

## 5. 管理端查数地图

### 数据中心

- “任务”：服务端事实库中的任务。
- “日程”：服务端事实库中的日程、阻挡块、课表等。
- “实际记录”：用户确认后的实际活动。
- “活动片段”：服务端活动理解生成的候选片段、置信度和状态。
- “追踪上传批次”：客户端原始追踪上传批次和处理结果。
- “排程运行”：服务端排程模型运行记录、草案和未排原因。

### 同步与客户端

- “客户端设备”：设备在线状态、最近心跳、待同步数、失败数、冲突数。
- “服务端变更日志”：服务端 canonical 数据产生的增量变更。
- “客户端 mutation”：客户端离线写入、失败队列、重试和错误信息。
- “同步冲突”：多端或版本冲突，不能静默覆盖，需要人工处理。

### 监控与日志

- “监控与日志”：查看 health、失败队列、错误聚合、审计日志、后台任务异常。
- “最近审计”：确认关键动作是否留下审计，例如 tracking ingest、report generated、scheduler run 等。

## 6. 端到端验收流程

按下面步骤可以验证一次完整闭环：

1. 服务端启动，`GET http://localhost:3200/api/health` 返回健康信息。
2. Web 管理端打开，服务端状态显示在线。
3. Windows 客户端“服务端同步”页填写 `http://localhost:3200/api`。
4. 点击“启动检查并同步”，客户端变为在线或服务端事实库模式。
5. 客户端产生一段追踪数据。
6. 点击“立即同步全部”。
7. 管理端“同步与客户端 / 客户端设备”里能看到该设备最近心跳。
8. 管理端“数据中心 / 追踪上传批次”出现新批次。
9. 批次状态为 `completed` 或 `completed_with_rejections`。
10. 如已运行活动理解，管理端“活动片段”出现候选片段。
11. 用户确认活动片段后，管理端“实际记录”出现对应记录。
12. 若确认时关联任务，任务投入和后续排程可以读取这段实际工作。

验收成功标准：

- Windows 客户端连接服务端并显示在线。
- 管理端能看到该客户端设备心跳。
- 追踪上传批次有记录，且不是长期停留在 `open` 或 `receiving`。
- 服务端能看到活动片段或实际记录。
- 同步失败和 mutation 失败数量不会持续增长。

## 7. 常见问题排查

### 客户端先红后绿

现象：Windows 客户端打开后先显示红色错误，稍后变成绿灯并正常连接。

处理：

1. 如果绿灯后“最后错误”不再更新，可以视为启动期临时错误。
2. 如果每次都出现同一业务错误，记录错误全文。
3. 优先查看“服务端同步”页的最后错误。
4. 再看管理端“同步与客户端 / 客户端 mutation”是否有失败记录。

### 追踪批次 completed_with_rejections

现象：批次完成，但有 `rejectedEventCount`。

处理：

1. 打开“追踪上传批次”详情。
2. 查看 `rejectedEventCount` 和原始 JSON。
3. 如果拒绝数量很少，可以继续验收后续链路。
4. 如果大量拒绝，检查客户端上传记录的时间、类型、payload 字段。

### 追踪批次 failed

现象：批次状态为 `failed`。

处理：

1. 查看 `errorMessage`。
2. 确认服务端 schema 已执行。
3. 确认客户端服务端地址是 `/api` 结尾，例如 `http://localhost:3200/api`。
4. 确认设备没有被撤销，heartbeat 正常。
5. 重新点击“启动检查并同步”后再上传。

### 管理端没看到追踪数据

排查顺序：

1. 客户端是否真的产生了追踪数据。
2. “服务端同步”页是否显示在线。
3. 是否点击过“立即同步全部”。
4. 管理端“客户端设备”是否看到该设备心跳。
5. 管理端“追踪上传批次”是否为空。
6. 管理端“客户端 mutation”是否有失败。
7. 客户端本地是否存在 `tracking.upload.last_error` 相关错误提示。

### 等待同步不归零

处理：

1. 打开管理端“同步与客户端 / 客户端 mutation”。
2. 按 `status` 查看失败、冲突、等待中的记录。
3. 重点看 `objectType`、`lastError`、`baseServerVersion`。
4. 如果是版本冲突，再看“同步冲突”。
5. 如果是服务端 4xx/5xx，按错误正文修复输入或服务端状态。

### 服务端可达但查不到数据

处理：

1. 确认管理端登录用户 ID 与客户端请求头中的用户一致。
2. 确认管理端 API 地址和客户端 API 地址指向同一个服务端。
3. 查看服务端 `/api/health`。
4. 查看管理端“服务端变更日志”是否有对应对象类型。
5. 查看“客户端 mutation”是否上传成功但被服务端拒绝。

## 8. 快速定位表

| 想确认的事情 | 管理端入口 | 成功信号 |
|---|---|---|
| 客户端是否在线 | 同步与客户端 / 客户端设备 | 最近心跳更新，状态 online |
| 本地写入是否上传 | 同步与客户端 / 客户端 mutation | 没有持续 failed，acked 增加 |
| 服务端是否产生变更 | 同步与客户端 / 服务端变更日志 | 出现对应 objectType |
| 追踪是否上传 | 数据中心 / 追踪上传批次 | completed 或 completed_with_rejections |
| 活动是否被理解 | 数据中心 / 活动片段 | 出现 candidate/confirmed 片段 |
| 用户是否确认实际发生 | 数据中心 / 实际记录 | 出现 confirmed 实际记录 |
| 报告是否引用证据 | 报告与推送 / 报告条目、报告证据 | 有 fact/inferred/evidence 链接 |
| 排程是否读取实际投入 | 数据中心 / 排程运行、任务投入 | run snapshot 或 task work 有记录 |

## 9. 注意事项

- 本手册不要求运行 Dart 或 Flutter 命令。
- 追踪上传不会上传键盘输入原文，只上传输入统计和活动元数据。
- `completed_with_rejections` 不一定表示全链路失败，要看拒绝比例和后续活动片段是否生成。
- 管理端看到的是服务端事实库，不等于客户端本地缓存的全部内容。
- 活动片段是候选理解结果，只有用户确认后才成为“实际记录”。
